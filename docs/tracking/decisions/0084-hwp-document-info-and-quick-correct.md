# 0084 한글 탭에 문서 정보(글자 수)와 빠른 교정(곡선따옴표)을 넣는다

## 맥락

외부 사용자 의견이 2026-10-28에 한 줄로 두 가지를 함께 보내왔다(0.12.5, Windows 11).

1. 한글(HWP)에서 **글자 수(공백 포함·공백 제외)** 를 볼 방법이 없다. 문서를 만들 때 글자 수를 맞춰야 해서 한글의 `Ctrl+Q,I` 문서 정보를 자주 본다.
2. 따옴표가 **언제나 직선**으로 들어간다. 한글은 곡선따옴표로 바뀐다.

확인한 것:

- rhwp-studio에는 문서 통계가 없다. 엔진의 `getDocumentInfo()`는 판·글꼴 목록·쪽수만 준다.
- 워드 편집기는 이미 스마트 따옴표가 있다(`apps/docs/src/renderer/editor/autocorrect.ts`, 기본 켜짐). **한글 탭만** 없었다.
- 기준은 한컴오피스다. 한컴 도움말을 확인했다.
  - 문서 정보는 **파일 → 문서 정보**, `Ctrl+Q,I`. `[문서 통계]` 탭에 글자(공백 포함)·글자(공백 제외)·글자에 포함된 한자 수·낱말·줄·문단·쪽·원고지(200자 기준)·표·그림·글상자를 보여 준다. 표는 **칸 하나를 문단 하나**로 센다.
  - 따옴표는 **도구 → 빠른 교정 → 빠른 교정 내용 → 입력 자동 서식**에서 바꾼다. 규칙은 언어가 아니라 **앞 글자**다: 앞에 공백이 있으면 여는 따옴표(“), 공백이 아닌 문자가 있으면(앞이 따옴표인 경우 포함) 닫는 따옴표(”)로 바꾼다. 신고자가 적은 "한글 입력이면 곡선, 영문이면 직선"은 한컴 문서와 다르다.

## 결정

**두 가지 다 편집기 안(studio)에서 앱 모듈로 만든다. 엔진과 저장 바이트는 건드리지 않는다.**

### 문서 정보

- 새 파일 `apps/hwp/studio-plugin/document-info.mjs`가 **엔진 호출만으로** 센다. 엔진에 통계 함수를 더하지 않는다(Rust 재빌드가 필요하다).
- 항목은 한컴의 `[문서 통계]`와 같게: 글자(공백 포함), 글자(공백 제외), 글자에 포함된 한자 수, 낱말, 줄, 문단, 쪽, 원고지(200자 기준), 표, 그림, 글상자.
- 셈 규칙도 한컴을 따른다.
  - 공백과 탭은 글자(공백 포함)에서 한 글자, 글자(공백 제외)에서는 빠진다.
  - 낱말은 공백 사이의 한 묶음(어절)이다.
  - **표의 칸 하나가 문단 하나**다. 표 안의 표도 센다.
  - 원고지 매수는 본문 글자(표·그림·글상자 밖)를 200으로 나눠 올림한 값에 표·그림·글상자 하나씩을 더한 값이다(한컴 도움말의 계산).
  - 머리말·꼬리말·각주·미주는 글자 수에서 뺀다. 한컴도 그것들은 원고지 계산에만 넣는다.
- 줄 수는 엔진의 조판(`getLineInfo`·`getLineInfoInCell`)이 주는 값을 쓴다. 조판이 아직 닿지 않은 문단은 1줄로 센다. 표 안의 표는 엔진에 경로로 묻는 줄 정보가 없어 문단마다 1줄로 센다.
- 대화상자는 편집기의 `ModalDialog`와 앱의 대화상자 껍데기(`studio-plugin/dialog-theme.mjs`)로 만든다. 버튼은 한컴처럼 `닫기` 하나다.
- 여는 길은 한컴과 같다: `Ctrl+Q,I`(한컴 도움말이 함께 적는 `Ctrl+Q,D`도)와 **파일 메뉴 → 문서 정보**(인쇄 아래).
- 큰 문서를 배려해 대화상자를 먼저 띄우고 `setTimeout` 뒤에 숫자를 채운다.

### 빠른 교정(곡선따옴표)

- 빌드 패치 `studio-quick-correct` 하나를 더한다. 편집기의 입력 처리(`engine/input-handler-text.ts`)가 글자를 문서에 넣기 전에 앱 모듈의 `quickCorrectTyped`(hancom-keys.mjs)를 한 번 부른다.
- 규칙은 한컴 그대로다: `"`·`'`를 앞 글자가 공백이거나 문단 시작이면 `“`·`‘`, 아니면 `”`·`’`로 바꾼다.
- **바꾸지 않는 것**: 붙여넣기·끌어놓기(`inputType`), IME 조합 중인 글자, 머리말·꼬리말·각주(커서 자리를 읽는 경로가 본문과 달라 v1에서 제외).
- 실행 취소는 지금처럼 한 글자에 한 단계다.

## 버린 대안

- **앱 바깥 React 대화상자**: 편집기(iframe)와 겉모습이 따로 놀고, `Ctrl+Q,I`를 편집기가 먼저 먹는다.
- **엔진의 평문 내보내기(`getTextFileText`)로 세기**: 일부 문서에서 표를 통째로 빠뜨린다(AI 읽기가 표를 보충하는 이유). 글자 수가 조용히 적게 나온다.
- **AI 플러그인에 계산을 맡기기**: AI 창이 떠 있어야 하고, 문서 정보는 AI와 무관하다.
- **입력 언어로 곡선/직선을 가르기**: 한컴 규칙과 다르고, Electron에서 한글 입력 상태를 안정적으로 알 수 없다. 여는/닫는 따옴표는 어차피 언어로 정할 수 없다.
- **WASM 엔진에 통계 함수 추가**: Rust와 wasm-pack으로 다시 빌드해야 한다. 지금 있는 호출로 충분하다.

## 결과

- `apps/hwp/studio-plugin/document-info.mjs`(새 파일), `hancom-keys.mjs`(명령·연속키·메뉴·`quickCorrectTyped`), `scripts/rhwp-patches.mjs`(패치 `studio-quick-correct`, `hancomHooks`), `scripts/build-studio.mjs`(스탬프에 새 모듈), `tests/document-info.test.ts`(새 파일), `tests/hancom-keys.test.ts`, `tests/hancom-commands.test.ts`, `tests/rhwp-patches.test.ts`.
- 실제 엔진으로 센 값이 손으로 센 값과 같다(글자 41·공백 제외 34·낱말 13·한자 2·문단 8·표 1·원고지 2). 대화상자 테스트는 JSDOM에서 항목과 `닫기` 하나를 본다.
- 빌드한 편집기에서 `Ctrl+Q,I`, 파일 메뉴, 따옴표 입력은 **사람이 실제 앱에서 확인해야 한다**(단위 테스트는 키 입력과 iframe 너머를 재현하지 못한다).
- 남은 것: 표 안의 표 줄 수(경로로 묻는 호출이 없다), 머리말·각주 안의 곡선따옴표, 빠른 교정 켜고 끄기 설정(한컴은 도구 → 빠른 교정에 있다).
