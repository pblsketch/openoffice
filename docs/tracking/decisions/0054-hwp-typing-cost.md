# 0054 — 한글 편집기의 입력 비용은 편집기와 엔진에서 줄이고, 저장 상태는 변경 알림으로 받는다

## 맥락

외부 사용자 신고 2건(0.12.2, Windows): 한글 문서에서 글자를 칠 때 살짝 버벅인다. 노트북과 데스크톱, 한글과 영어, AI 창을 닫았을 때와 열었을 때, 50쪽 문서와 새 빈 문서 모두 같다고 했다.

앱 쪽에서 의심한 것은 두 가지였다. 저장 상태를 0.4초마다, 그리고 키를 칠 때마다 50ms 뒤에 편집기에 묻는 것(`App.tsx`)과, AI 창이 접혀 있어도 0.7초마다 선택을 묻는 것(`AiPanel.tsx`)이다. 빌드한 앱을 격리된 임시 사용자 폴더로 띄워 CDP로 키를 치며 쟀다(1초에 10타, 5초씩, 회차마다 새 문단).

- 두 확인은 한 번에 0.02~0.05ms다. 둘을 끄고 켠 네 경우의 차이는 측정 잡음(±5%) 안이었다. 엔진의 `pageCount()`는 이미 나눈 쪽 수를 더할 뿐이라 쪽 나누기를 앞당기지 않는다.
- 시간은 편집기 안에서 쓰였다. 키 하나에 편집기는 보이는 쪽을 다시 그리고 문서 전체에서 캔버스 측정 요청을 모은다.
  1. **글꼴 치환.** 편집기는 캔버스의 `font` 설정을 가로채 글꼴 이름마다 대체 글꼴 목록을 새로 만든다. 쪽 하나를 그릴 때 같은 이름이 수천 번 온다. 빈 문서에 한 쪽쯤 치면 바쁜 시간의 70%가 여기였다.
  2. **측정 요청 수집.** 편집마다 엔진의 `collectCanvasMetricRequests`가 문서의 모든 글자 묶음에 `trace_char_width_decisions`를 부르고, 그 함수는 탭의 폭을 채우려고 묶음 전체의 글자 위치를 잰다. 50쪽 시험 문서는 요청이 0개인데도 키마다 약 135ms를 썼다.
- 한글 조합(IME)도 같은 두 곳을 지난다. 글자 하나에 조합 갱신이 2~3번이라 영어보다 무겁다.
- 신고의 "문서 크기와 상관없다"는 맞지 않았다. 빈 문서도 칠수록 무거워지고, 50쪽 문서는 처음부터 무겁다.
- 재다가 다른 결함을 찾았다. 저장 상태는 키를 친 50ms 뒤에야 편집기에 물어 메인에 알렸고, 메인은 탭을 닫을 때 그 사본만 본다. 빈 문서에 한 글자를 치고 바로 탭을 닫으면 6번 모두 확인 창 없이 닫혀 고친 내용이 사라졌다(1초 기다린 뒤 닫으면 떴다). 50쪽 문서는 편집기가 느려 우연히 피했다.

## 결정

1. **편집기 빌드 패치로 글꼴 치환의 답을 기억한다(`studio-font-memo-state`, `studio-font-memo-use`).** 같은 글꼴 이름의 답을 다음 마이크로태스크 지점까지만 기억한다. 답이 기대는 것(찾은 PC 글꼴, 문서의 글꼴 대체 표)은 비동기 단계가 끝날 때만 바뀌므로 결과는 같다. 상위 `devel`은 같은 일을 그리기 한 번 단위로 이미 고쳤다(`b3eaf7b10`, #7897, 10월 14일). 0.8.7에는 없어서 그 수정을 받을 때까지 쓰고, rhwp를 그 뒤 버전으로 올리면 뺀다.
2. **엔진 패치 0015: 요청 수집은 글자 위치를 재지 않고 폭의 출처만 본다.** 위치는 탭에만 쓰이는데 수집기는 탭을 건너뛴다. 탭이 아닌 글자의 판정이 원래 함수와 같은지 단위 시험으로 지키고, 요청 묶음은 바뀌지 않는다. 상위 `devel`에도 같은 비용이 있어 이슈로 냈다([#8162](https://github.com/edwardkim/rhwp/issues/8162)).
3. **저장 상태는 편집기의 변경 알림으로 받는다.** 앱의 플러그인이 편집기의 `document-dirty-changed`를 받아 편집과 같은 작업 안에서 편집기 창에 `ieum:dirty-changed`를 쏘고, 앱이 곧바로 메인에 알린다. 키마다 예약하던 확인은 없앴고, 묻는 것은 플러그인이 올라온 직후 한 번과 2초마다의 안전망만 남겼다. 묻는 동안 알림이 오면 그 답은 버린다(낡은 "고치지 않음"이 새 상태를 덮지 않게). 속도 때문이 아니라 위의 결함 때문이다. 빌드한 앱에서 한 글자를 치고 바로 닫으면 빈 문서 6/6, 50쪽 문서 3/3, 한글 조합 중 3/3 확인 창이 뜨고, 고치지 않은 문서는 뜨지 않는다.
4. **AI 창의 선택 조회는 바꾸지 않는다.** 선택이 없을 때 한 번에 0.02ms이고, 끄고 켠 차이가 측정 잡음 안이었다.

## 택하지 않은 것

- **메인이 탭을 닫을 때마다 편집기에 저장 상태를 다시 묻는다.** 가장 확실하지만 닫기 경로(`hwp-main.ts`)를 바꾸고, 편집기가 멈춘 탭은 닫히지 않게 된다. 알림이 편집과 같은 작업에서 나가므로 그만큼 필요하지 않다.
- **AI 창이 접혀 있으면 선택 조회를 멈춘다.** 줄어드는 시간이 없다.
- **측정 요청을 지난 수집의 결과에서 다시 쓴다(글자 묶음과 글자 모양이 같으면).** 만들어 문서 55개에서 결과가 같은 것까지 확인했지만, 2번을 넣고 나면 50쪽 문서에서 1.5ms(약 7%)만 줄고 문서 크기만큼 기억을 더 쓴다. 남는 비용은 묶음을 만드는 줄 구성이라, 바뀐 문단만 다시 모으는 상위 수정이 맞다.
- **키를 칠 때 측정 요청 수집이나 쪽 다시 그리기를 미룬다.** 측정이 늦게 붙으면 글자 폭이 바뀌어 줄이 한 번 더 움직인다. 같은 일을 더 싸게 하는 쪽만 택한다.

## 결과

빌드한 앱에서 CDP로 1초에 10타씩 5초 쳐서 견줬다. "메인 스레드"는 키 하나에 쓴 렌더러 메인 스레드 시간, "반응"은 키를 누른 때부터 다음 화면 틀까지다.

| 경우                                   | 메인 스레드(키당)                          | 반응 중앙값 / 느린 5% | 잃은 화면 틀(회차당) |
| -------------------------------------- | ------------------------------------------ | --------------------- | -------------------- |
| 빈 문서, 고치기 전(새 문단 5회차 평균) | 45.7ms (1회차 9.7 → 5회차 75.6으로 늘어남) | 8.7 / 16.1ms          | 56                   |
| 빈 문서, 고친 뒤                       | 11.5ms (10~12로 그대로)                    | 8.9 / 16.4ms          | 0.2                  |
| 50쪽 문서, 고치기 전                   | 317ms                                      | 336 / 421ms           | 892                  |
| 50쪽 문서, 고친 뒤                     | 102ms                                      | 84 / 102ms            | 202                  |
| 50쪽 문서 한글 조합, 고치기 전         | 391ms(조합 갱신당)                         |                       |                      |
| 50쪽 문서 한글 조합, 고친 뒤           | 105ms(조합 갱신당)                         |                       |                      |

- "고친 뒤"는 세 변경을 모두 넣은 빌드다. 저장 상태 알림을 넣기 전 빌드는 50쪽 문서에서 141ms(반응 116 / 127ms)였다. 차이의 원인은 가리지 않았다(앞서 확인 주기를 끄고 켠 견줌에서는 차이가 잡음 안이었으므로 측정 사이의 차이일 수 있다).
- 엔진 수집 한 번(WASM, node): 50쪽 문서에서 중앙값 153ms → 89ms.
- 50쪽 문서에서 남은 시간의 대부분은 수집의 줄 구성(문서 전체)과 보이는 쪽 다시 그리기다. 바뀐 문단만 다시 모으는 것은 상위에서 할 일이라 이슈에 함께 적었다.
- 저장·내보내기 결과는 바뀌지 않는다. 0015는 요청 묶음을 바꾸지 않고(탭이 아닌 글자의 판정이 같다), 글꼴 기억은 같은 답을 다시 쓸 뿐이다.
