# 0063 — 설정 파일의 키를 Windows와 Linux에서 운영체제 암호화로 저장하고, 명령어는 앱에게 풀어 받는다

## 맥락

2026-10-22에 받은 외부 소스 점검이 짚었다. 키 제공자의 키, 이미지·분석·검색 제공자의 키, 직접 운영하는 서버의 키, GitHub 읽기 토큰이 `ai-settings.json`에 평문으로 있다. 드라이브의 갱신 토큰은 운영체제 암호화(`safeStorage`)로 둔다(결정 0033).

그동안 평문으로 둔 이유는 터미널 명령어와 MCP 때문이었다. 둘은 Electron 없이 같은 파일을 읽고 저장된 키를 쓴다(`pdf ai-read`의 키 제공자, 검색 키). `safeStorage`는 Electron 안에서만 된다.

운영체제 암호화가 막아 주는 범위도 적어 둔다. Windows의 암호화(DPAPI)는 그 사용자 계정에 묶인다. 같은 계정으로 도는 프로그램은 풀 수 있다. 막아 주는 것은 파일이 복사되거나, 동기화되거나, 백업에 들어가거나, 다른 계정이나 다른 PC에서 읽히는 경우다.

## 결정

**봉인.** 앱 뒷단은 Windows와 Linux(실제 키링이 있을 때)에서 키와 토큰을 `safeStorage`로 암호화해 같은 자리에 `sealed:v1:<base64>`로 쓴다. 대상은 `providers.*.apiKey`, `customEndpoints[].apiKey`, `media.providers.*.apiKey`, `search.providers.*.apiKey`, `readUrl.githubToken`이다. 파일의 모양은 그대로이고, 사람이 손으로 적은 평문 키도 그대로 읽힌다. 다음에 앱이 저장할 때 봉인된다.

- 봉인은 `@genoffice/ai-provider`의 `sealAiSecrets`가 하고, 설정을 쓰는 곳(워드 뒷단의 저장 두 곳, 슬라이드·엑셀의 따로 실행용 저장)이 디스크에 쓰기 직전에 부른다. 풀기는 `resolveAiSettings`가 맨 앞에서 한다. 그래서 파일을 읽는 모든 곳이 평문 키를 받는다. 화면 쪽 창은 지금처럼 뒷단이 푼 설정을 받는다.
- 무엇으로 봉인하고 풀지는 프로세스가 등록한다(`setAiSecretCodec`). 앱은 준비가 끝나자마자 `safeStorage`를 등록한다. 등록이 없거나 풀지 못하면 그 값은 빈 키로 읽힌다. 봉인된 글자가 키로 보내지는 일은 없고, 요청은 "키 없음"으로 끝난다.
- 앱이 시작할 때(단일 실행 잠금을 얻은 뒤) 파일에 평문 키가 남아 있으면 한 번 봉인해 다시 쓴다. 예전 판이 쓴 파일이 이렇게 옮겨진다.
- 봉인은 Chromium의 암호화 키가 디스크(데이터 폴더의 `Local State`, `os_crypt.encrypted_key`)에 적힌 뒤에만 한다. Chromium은 키를 처음 쓸 때 만들고 10초쯤 뒤나 정상 종료 때 적는다(2026-10-22 이 PC의 Electron에서 확인: 바로 `app.exit()`하면 적히지 않고, 다른 프로세스는 그 값을 풀지 못했다). 그 사이에 앱이 죽으면 봉인한 키를 영영 풀 수 없게 되므로, 키가 디스크에 없으면 평문으로 두고 다음 저장이나 다음 시작 때 봉인한다. 그래서 처음 업데이트한 날의 첫 실행에서는 봉인되지 않을 수 있다.
- **Linux는 실제 키링일 때만 봉인한다(2026-10-23 추가).** Electron이 고른 저장소(`getSelectedStorageBackend`)가 GNOME 키링(`gnome_libsecret`)이나 KWallet(`kwallet`, `kwallet5`, `kwallet6`)일 때만이다. 데스크톱 환경을 알아보지 못하거나 키링이 없으면 Chromium은 프로그램에 박힌 키로 "암호화"하는 `basic_text`로 떨어진다. 그 값은 보호받는 것처럼 보일 뿐이라 평문으로 둔다. 키링은 키를 바로 저장하므로 Windows처럼 `Local State`를 기다리지 않는다. 명령어가 띄운 앱도 같은 키링에 닿아야 풀린다. SSH로 들어온 터미널처럼 데스크톱 세션의 키링에 닿지 못하는 곳에서는 빈 키가 된다.
- **macOS는 봉인하지 않는다.** macOS의 `safeStorage`는 키체인을 쓰고, 키체인은 앱의 서명을 보고 접근을 허락한다. Mac판은 ad hoc 서명뿐이라(결정 0031) 빌드마다 앱의 서명이 달라져, 새 버전을 설치할 때마다 "키체인의 기밀 정보를 사용하려고 한다"는 창과 로그인 암호를 물을 가능성이 크다. 업데이트마다 뜨는 창은 읽지 않고 누르게 만들고, "거부"를 누르면 키가 비어 다시 넣어야 한다. 저장소 주인이 Mac에서 확인할 수도 없다. Apple 개발자 서명(Developer ID)을 하게 되면 그때 켠다. 그전에는 Mac의 설정 파일이 그 계정만 읽을 수 있는 폴더(`~/Library/Application Support`)에 있다는 것이 보호의 전부다.
- 봉인하지 않는 곳도 봉인된 값을 만나면 풀기는 시도한다.

**터미널 명령어.** 명령어는 봉인된 값을 처음 만나면 앱을 창 없이 `--reveal-ai-secrets`로 띄운다. 그 파일의 봉인된 값들을 표준 입력으로 넘기고, 표준 출력 한 줄로 평문을 받아 그 프로세스의 메모리에만 둔다. 설정 파일마다 프로세스당 한 번이다. 그래서 MCP 서버처럼 오래 도는 프로세스도 한 번만 띄운다. 앱을 찾지 못하거나 풀지 못하면 빈 키다. 명령어는 봉인하지 않는다.

- `--reveal-ai-secrets`는 단일 실행 잠금, 창, 렌더러 프로토콜보다 먼저 처리하고 끝난다. 받는 것은 봉인된 값의 목록(64개, 값 하나 16KB까지)뿐이고, 그 밖의 입력이면 오류 한 줄로 끝난다.
- 이 입구는 같은 계정의 아무 프로그램이나 부를 수 있다. 같은 계정의 프로그램은 DPAPI를 직접 불러도 풀 수 있으므로, 보호 범위를 넓히지 않는다.
- 띄우는 앱이 봉인한 앱과 같은 데이터 폴더를 써야 풀린다. 설치본은 같은 폴더를 쓴다. 저장소에서 띄우는 개발용 앱에는 `GENOFFICE_USER_DATA`로 설정 파일의 폴더를 넘긴다.

## 택하지 않은 것

- **앱만 암호화하고 명령어는 환경 변수의 키만 쓴다.** 단순하지만 명령어에서 저장된 키가 갑자기 쓰이지 않게 되어, 약속(`docs/contracts.md`)이 바뀐다.
- **명령어가 Chromium의 암호화 형식을 직접 푼다(`Local State`의 키를 PowerShell로 DPAPI 해제 후 AES-GCM).** 앱을 띄우지 않아 빠르지만, Electron 안쪽 형식에 기대므로 Electron을 올릴 때 조용히 깨질 수 있다.
- **봉인한 값을 다른 칸(`apiKeySealed` 등)에 둔다.** 예전 판과 손으로 고치는 사람이 두 칸을 함께 이해해야 하고, 한쪽만 고치면 어긋난다.
- **암호화를 못 하는 PC에서는 키를 저장하지 않는다(드라이브처럼).** 키는 앱을 켤 때마다 다시 넣을 수 없는 값이다. 그런 PC는 지금처럼 평문으로 둔다.

## 결과

- Windows와 키링이 있는 Linux에서 설정 파일을 복사하거나 백업해도 키가 보이지 않는다. 다른 PC나 다른 계정으로 옮긴 설정 파일의 키는 풀리지 않으므로 다시 넣어야 한다. Windows에서 데이터 폴더의 `Local State`를 지우거나 Linux에서 키링의 항목을 지워도 마찬가지다.
- macOS는 평문이다. 개발자 서명을 하는 결정이 나면 이 결정을 다시 연다.
- 터미널 명령어는 봉인된 키를 처음 읽을 때 1~2초 더 걸린다.
- 홈 검색의 재정렬 키(`app-settings.json`의 `fileSearch.keys`)도 같은 방식으로 봉인한다. 앱만 읽는 파일이라 명령어 쪽 일은 없다. 정리 함수가 키를 다듬고 자르므로 읽을 때는 정리 전에 풀고, 쓸 때는 정리 뒤에 봉인한다.
