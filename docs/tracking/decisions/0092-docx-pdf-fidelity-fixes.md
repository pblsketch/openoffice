# 0092 — 워드 → PDF 결함 넷을 이 저장소에서 고치고, 엔진의 원본과 다른 점을 목록으로 지킨다

## 맥락

워드 문서를 PDF로 내보낸 결과에 결함 넷이 있다는 신고가 왔다(0.12.8, `ieumoffice convert file.docx --to pdf`). 같은 내용이 원본 저장소에도 이슈로 올라가 있다(genspark-ai/genoffice#2331). 넷 다 이 PC에서 재현했다.

1. 꼬리말의 `SECTIONPAGES`(구역 쪽 수) 필드가 비어 `- 9 / `로 나왔다.
2. 목차 첫 줄이 `1. 총칙 ......... 1` 대신 `1. 총칙1`로 나왔다.
3. 표지의 색 띠가 오른쪽 아래로 밀렸다.
4. PDF의 한국어 글꼴이 모두 Type3여서 글자를 찾거나 복사하기 어렵고, PDF/A식 글꼴 검사에도 걸렸다.

원인은 다음과 같다. 1~3은 워드 엔진(`packages/docx-engine`) 안에, 4는 앱이 넣어 둔 글꼴 파일에 있다.

1. 머리글·꼬리말을 읽는 코드가 `PAGE`와 `NUMPAGES`만 쪽 번호 필드로 알아봤다. `SECTIONPAGES`는 미리 저장된 값을 보여 주는 길로 빠졌다. 그 값이 필드 표시와 같은 런에 있으면(python-docx가 그렇게 쓴다) 버려졌고, 남더라도 고정된 "1"이었다.
2. 목차 필드가 시작되는 문단은 스타일 이름이 `toc N`이거나 그 문단에 직접 오른쪽 탭이 있을 때만 목차 줄로 읽혔다. 직접 만든 목차 스타일("목차 1")에만 점선 탭이 있으면 일반 글로 빠졌다. 일반 글 길은 탭을 버린다.
3. 쪽 기준 도형에 "위아래 배치"나 "사각형 배치"가 걸려 있으면 엔진이 쪽 좌표를 버리고 본문 흐름에 쌓았다. 그래서 왼쪽·위 여백만큼 밀렸다. 쪽 기준 세로 정렬(`wp:align`)도 쓰이지 않았다.
4. Windows의 Chromium은 PDF에 CFF 윤곽 글꼴을 Type3로 쓴다. 앱이 넣어 둔 한국어·중국어 글꼴(대체 글꼴 다섯, 템플릿의 Noto Serif KR 둘)이 모두 CFF였다. 같은 글꼴을 TrueType 윤곽으로 바꾸면 TrueType으로 심어진다.

## 결정

- **1~3을 워드 엔진에서 고친다.** 사용자가 승인했다. 엔진 규칙은 "엔진 동작은 원본의 수정이 병합될 때만 바뀐다"였다. 이 수정부터는 pdf2docx(결정 0058)처럼 `packages/docx-engine/AGENTS.md`의 "원본과 다른 점"에 적고 시험으로 지킨다. 같은 수정을 원본 #2331에 PR로 보내고, 원본이 받아들이면 원본 코드로 돌아간다.
- **엔진이 고치는 것은 읽기와 표시다.** 저장이 달라지는 경우는 하나뿐이다. 고친 머리글·꼬리말을 저장할 때 `SECTIONPAGES`를 필드 그대로 다시 쓴다. 전에는 글자 "1"로 굳었다. 고치지 않은 문서는 예전처럼 원본 바이트 그대로 저장된다.
- **표지 도형은 본문과 새로 겹치지 않는 경우만 쪽 위치로 옮긴다.** 본문 맨 위를 덮는 "위아래 배치" 띠, 칸 전체 폭 도형, 본문 영역 밖(여백, 쪽 가장자리)에 통째로 있는 도형이다. 칸 안의 좁은 "사각형·빽빽하게·투과" 상자와 쪽 아래쪽의 좁은 "위아래 배치" 상자는 예전처럼 흐름에 둔다. 그런 상자를 쪽 위치로 옮기면 주변 글이 비켜 흐르지 못해 글자와 겹친다.
- **앱이 넣어 둔 CFF 글꼴을 TrueType 윤곽으로 바꾼다.** 결정 0013의 "원래 배포처의 파일을 고치지 않고 그대로 넣는다"는 템플릿의 Noto Serif KR 두 파일에 한해 바뀐다. 사용자가 승인했다. 글자 수, 글자 폭, 줄 높이 치수는 그대로이고, 윤곽은 이차 곡선으로 근사한다(오차 1 단위 안팎). 변환 도구는 `tools/convert-cff-to-glyf.py`다.
- **Pretendard는 바꾸지 않는다.** 라이선스(OFL)의 예약 글꼴 이름이 "Pretendard"라서, 고친 파일이 같은 이름을 쓸 수 없다. 이 글꼴로 쓴 글은 PDF에 계속 Type3로 들어간다.

## 택하지 않은 것

- **원본에서 고쳐지기를 기다리기.** 원본은 비공개 저장소에서 개발해 묶음 커밋으로 내보낸다. 언제 받아들여질지 알 수 없고, 그동안 매일 PDF를 만드는 사용자가 같은 결함을 겪는다.
- **화면 쪽에서만 덧대기.** 1과 2는 엔진이 필드 명령이나 탭을 버린 뒤에 화면에 넘어오므로 화면에서는 되살릴 수 없다.
- **표지의 모든 쪽 기준 도형을 쪽 위치로 옮기기.** 처음 그렇게 고쳐 보니 칸 안의 좁은 상자가 본문 글자를 덮었다. 예전에는 자리는 틀려도 겹치지는 않았다. 겹침은 자리가 틀린 것보다 읽기 어렵다.
- **PC에 설치된 Noto Serif KR을 먼저 쓰기.** 신고자 PC에서는 풀리지만 PC마다 글꼴 판이 달라 배치가 조금씩 달라진다. 결정 0013이 템플릿 글꼴을 넣은 까닭과 어긋난다.
- **PDF 내보내기를 다른 프로그램으로 돌리기.** 화면에 보이는 것과 내보낸 것이 같다는 지금 구조(`docs/headless-pdf-export.md`)를 깬다.

## 결과

- 꼬리말의 `SECTIONPAGES`가 그 쪽이 속한 구역의 쪽 수로 나온다. 화면, 쪽 사이 띠, 미리보기, PDF, 머리글 편집기가 같은 값을 쓴다. AI가 읽는 머리글 글에는 `{SECTIONPAGES}`로 보인다.
- 직접 만든 스타일의 목차도 점선 탭과 쪽 번호가 제자리에 나온다.
- 표지의 색 띠가 제자리에 그려지고, 쪽 맨 아래 띠가 다음 쪽으로 밀리지 않는다. 좁은 제목 상자는 예전처럼 여백만큼 밀린 채로 남는다(`findings.md`).
- 대체 글꼴 다섯과 템플릿 Noto Serif KR이 PDF에 TrueType으로 심어진다. Windows에서 대체 글꼴 셋(GenOffice Sans/Serif/Che Latin KR)의 글자 폭이 바뀐다. 이 세 글꼴은 고친 폭을 `hmtx` 표에만 적고 CFF 안의 폭은 옛 값으로 두었는데, Windows의 Chromium은 CFF 쪽 폭으로 그렸다. 예를 들어 바탕 대체 글꼴의 한글은 0.966em, 라틴 'A'는 1.37em이었다. 바꾼 뒤에는 의도한 값(한글 1.0em, 'A' 0.736em)이 되어 Mac·시험과 같아진다. 바탕체가 없는 Windows PC에서는 바탕·명조 문서의 줄바꿈과 쪽 나눔이 바뀐다. 사용자가 이것을 받아들였다.
- 템플릿 글꼴 폴더가 커져 상한 `TEMPLATE_FONTS_MAX_BYTES`를 올린다. 설치 파일은 압축이 더 잘 되어 조금 작아진다.
- 원본을 받아올 때 `parse.ts`, `parse-fields.ts`, `parse-drawing-geometry.ts`, `patch.ts`, `types.ts`에서 충돌이 날 수 있다. "원본과 다른 점"의 시험이 그 충돌을 푼 결과를 지킨다(`docs/operations.md`).
- PC에 설치된 가변 글꼴(예: Windows의 `NotoSansKR-VF.ttf`)과 Pretendard, 템플릿의 라틴 가변 글꼴은 여전히 Type3로 들어간다. Chromium의 한계다(`findings.md`).
