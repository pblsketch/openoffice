# 0030 — PDF 도구는 홈의 카드와 별도 창으로 모으고, 일반 사용자의 말로 이름을 짓는다

## 맥락

PDF로 자주 하는 일(합치기, 나누기, 인쇄 준비, 변환, 용량 줄이기)의 절반 이상이 PDF 편집기에 이미 있다. 그런데 리본 여러 탭에 흩어져 있고, PDF를 먼저 열어야만 쓸 수 있다. 참고한 두 앱은 할 일부터 고르는 화면을 둔다. PDF LAB은 교사용 웹 앱이고, iLovePDF는 파일을 서버에 올리는 웹 서비스다.

이음오피스는 특정 직업군용이 아니고 21개 언어로 나간다. 그래서 PDF LAB의 학교 전용 용어("생활기록부 양면 모아찍기" 등)를 그대로 가져올 수 없다. 계획 전체는 `docs/plans/pdf-tools.md`에 있다.

## 결정

- 입구는 홈의 "PDF 도구" 카드와 별도 창이다. 셸의 만들기 창과 같은 방식이다. 편집기에는 새 리본 탭을 만들지 않고, 새 기능을 기존 탭의 알맞은 자리에 넣는다.
- 첫 배포 범위는 1단계(도구 창, 이미 있는 기능 연결)와 2단계(새 의존성 없는 새 도구)다.
- qpdf(Apache-2.0)는 3단계(암호 걸기·풀기, 파일 복구)에 들이는 쪽으로 간다. 설치 파일이 얼마나 커지는지 그때 재 보고 확정한다.
- 이미 있는 이름(PDF 병합, PDF 분할, 페이지 모아찍기, 페이지 추출, 역순 정렬)은 바꾸지 않는다. 카드의 한 줄 설명에서 쉬운 말로 풀어 준다.
- 새 이름은 계획 문서의 용어 대조표를 따른다. 특정 직업·기관의 서류 이름을 쓰지 않고, 이름에 결과까지 드러낸다(예: "빈 페이지 찾아 지우기", "양면 인쇄 맞추기", "배경 겹치기").
- 도구 화면은 "페이지"로 쓴다. 편집기 전체의 "페이지"/"쪽" 정리는 별도 과제다.
- 도구는 AI를 쓰지 않고, 원본을 바꾸지 않으며, 결과를 항상 새 파일로 저장한다.
- 2단계 끝에 "PDF 도구" 도움말 주제를 21개 언어로 더한다.

## 택하지 않은 것

- **편집기 리본에 "도구" 탭을 하나 더 만든다.** PDF를 먼저 열어야 하는 문제가 그대로 남고, 병합처럼 여러 파일을 받는 도구에는 맞지 않는다.
- **기존 이름을 쉬운 말(합치기·나누기)로 바꾼다.** 21개 언어 문구를 모두 다시 번역해야 하고, 바꾸는 동안 리본과 도구 창의 이름이 어긋난다.
- **PDF LAB의 용어와 활용 예시를 그대로 쓴다.** 교사가 아닌 사람에게 낯설고, 한국 학교 제도의 이름은 다른 언어로 옮길 수 없다.
- **AGPL 라이브러리(MuPDF, Ghostscript, CPDF)로 압축을 한다.** 의존성 라이선스 허용 목록 밖이다.

## 결과

- 이미 있는 기능을 찾기 쉬워진다. 1단계만으로도 새 라이브러리 없이 볼 수 있는 변화다.
- 도구 창은 셸에, 처리 코드는 PDF 편집기 모듈(`apps/pdf/src/main`)에 둔다. 셸을 다시 빌드해야 반영된다.
- 같은 기능이 리본과 도구 창 두 곳에 있게 되므로 문구 키를 같은 것으로 쓴다.
- 서버를 거치는 기능(휴대폰 스캔을 PC로 보내기)은 만들지 않는다.
