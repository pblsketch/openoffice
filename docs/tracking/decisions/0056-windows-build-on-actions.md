# 0056 — Windows 설치 파일을 GitHub Actions에서 만들고 출처 증명을 붙인다. 서명은 하지 않는다

## 맥락

2026-10-22에 받은 외부 소스 점검이 짚었다. Mac·Linux 설치 파일은 GitHub의 빌드 기계에서 만들지만(결정 0031), Windows 설치 파일은 저장소 주인의 PC에서 만들어 손으로 올린다. 사용자는 받은 설치 파일이 공개된 소스에서 만들어진 것인지 확인할 방법이 없다. 오픈소스용 무료 코드 서명 프로그램도 함께 권했다.

서명에는 되돌릴 수 없는 면이 있다. 서명한 버전이 한 번 배포되면 앱에 "이 게시자가 서명한 업데이트만 받는다"는 조건이 들어가, 그 뒤로는 서명 없이 만든 버전으로 업데이트되지 않는다(`docs/releasing.ko.md` 4번).

## 결정

- **빌드.** `.github/workflows/windows-build.yml`이 GitHub의 Windows 빌드 기계(`windows-2025`)에서 저장소 주인의 손 빌드와 같은 순서로 설치 파일을 만든다. 순서는 `npm ci`, `build:all`, 엑셀 처리 프로그램을 설치 파일 도구가 찾는 자리로 복사, `dist:win`이다. 비밀 값을 쓰지 않는다. Mac·Linux와 같이 `main`에서 손으로 실행하고, 릴리스 태그를 주면 공개된 그 릴리스에 설치 파일·`.blockmap`·`latest.yml`을 붙인다. 빌드한 버전과 태그가 같을 때만 붙인다.
- **검사.** 묶인 프로그램(엑셀 처리 프로그램, OCR 도우미, 명령어)이 있는지 본다. `latest.yml`의 버전·파일 이름이 설치 파일과 맞는지, 설치 파일에 **서명이 없는지**도 본다. 그다음 빌드한 앱을 창 없이 실행해 Markdown과 CSV를 PDF로 내보낸다.
- **출처 증명.** 손으로 실행한 빌드는 설치 파일과 `latest.yml`에 GitHub의 빌드 출처 증명(`actions/attest-build-provenance`)을 붙인다. 누구나 `gh attestation verify IeumOffice-Setup-<버전>.exe --repo pblsketch/openoffice`로 "이 저장소의 이 커밋을 이 워크플로가 만들었다"를 확인할 수 있다.
- **서명은 하지 않는다.** 서명 프로그램의 조건과 인증서를 유지하는 일은 저장소 주인이 따로 정한다. 정하기 전에 서명된 버전이 실수로 나가지 않도록 워크플로가 서명된 설치 파일을 거절한다.
- **손 빌드는 남긴다.** Actions 빌드가 실패하거나 GitHub를 쓸 수 없을 때를 위해 `docs/releasing.ko.md` 4번의 손 빌드 절차를 그대로 둔다. 손 빌드로 올린 파일에는 출처 증명이 없다.

## 택하지 않은 것

- **오픈소스 무료 서명을 바로 신청한다.** 한 번 서명하면 되돌릴 수 없고, 신청 조건과 서명 절차(서명 서비스에 빌드를 넘기는 방식)를 저장소 주인이 확인하지 않았다.
- **설치 파일의 해시만 릴리스 본문에 적는다.** 같은 사람이 파일과 해시를 함께 올리므로 출처를 보여 주지 못한다.
- **Windows 빌드를 커밋마다 돌린다.** 빌드 기계 시간이 길고(설치 파일까지 수십 분), 패키징 설정이 바뀌는 끌어오기 요청에서만 돌려도 깨짐은 잡힌다.

## 결과

- Windows 설치 파일도 공개 소스에서 만들어졌는지 사용자가 확인할 수 있다.
- 릴리스 순서가 바뀐다. 먼저 릴리스(프리릴리스)를 본문만으로 공개한다. 그다음 Windows·Mac·Linux 빌드를 각각 태그를 주어 실행한다. 세 파일 묶음이 붙은 것을 확인한 뒤 프리릴리스를 푼다.
- 첫 실행은 태그 없이 돌려 결과물을 받아 손 빌드와 같은지 확인해야 한다. 이 결정을 쓸 때는 Actions에서 아직 한 번도 돌리지 않았다.
- Windows 사용자가 보는 "알 수 없는 게시자" 경고는 그대로다.
