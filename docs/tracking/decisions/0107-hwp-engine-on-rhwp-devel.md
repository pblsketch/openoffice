# 0107 — 한글 엔진과 편집기를 배포 전 rhwp `devel` 커밋에 맞춘다

## 맥락

한글 편집기는 rhwp `v0.8.7`(2026-10-06)에 패치 28개를 얹은 엔진을 썼다(결정 0050). 편집기 화면(rhwp-studio)도 같은 태그에서 빌드했다.

2026-11-04 기준 상위는 새 배포판을 내지 않았다. `main`은 `v0.8.7`과 같은 커밋이고, 다음 판(`Cargo.toml`의 0.9.0)은 `devel`에서 준비 중이다. `devel`은 `v0.8.7`보다 4,157커밋 앞이고, 그사이 병합한 PR이 164개다. 그 가운데에는 우리가 낸 엔진 PR 넷(#8121, #8144, #8145, #8165)과 우리 패치가 옮겨 온 상위 수정(#7882, #8228)도 들어 있다.

2026-10-23에는 다음 배포판을 기다리기로 했다. 2026-11-04 저장소 주인이 배포판을 기다리지 말고 병합된 PR을 미리 앱에 넣으라고 했다.

## 결정

**엔진과 편집기를 상위 `devel`의 한 커밋(`7d06d5c70`, 2026-11-03)에 고정하고, 우리 패치를 그 위로 다시 옮겨 빌드한다.**

PR을 하나씩 골라 `v0.8.7`에 옮기는 방식은 쓰지 않는다. 통합 PR이 서로 기대고 있어 골라 옮기면 충돌이 크고, 다음 배포판에서 같은 일을 다시 해야 한다. `devel` 커밋 위에 패치를 옮겨 두면 0.9.0이 나왔을 때 태그만 바꾸면 된다.

- **고정 방식.** `vendor/rhwp-core/package.json`의 `rhwp.branch`가 `devel`이고 `rhwp.commit`이 고정한 커밋이다. `rhwp.tag`는 태그가 아니라 그 고정점의 이름(`devel-7d06d5c70`)이고, 빌드가 받아 둔 소스 폴더의 이름으로 쓰인다. `tools/build-rhwp-core.mjs`와 `apps/hwp/scripts/build-studio.mjs`는 `branch`가 있으면 그 커밋을 직접 받는다. 버전은 `0.9.0-devel.ieum.18`이다.
- **엔진 패치 28개는 18개로 줄었다.**
  - 상위에 이미 있어서 뺀 것(8개): 0002(#7704 등), 0008(#8144), 0009(#8145), 0010·0011(#8165), 0012(#7882), 0017(#7905), 0019(#8228).
  - 상위가 다르게 고쳐서 뺀 것(2개): 0006은 상위가 모든 구역에서 각주를 그리는 높이로 예약해 대신한다. 0007은 상위가 한컴 2024 인쇄본으로 확인한 규칙(`normal_hancom_full_width_table_owns_a_separate_row`)과 반대라서 상위를 따른다.
  - 일부만 옮긴 것: 0001과 0004는 상위가 받아 가면서 고쳐 쓴 판(#8388)에서 빠진 경우(제목 문단에 그림이 함께 든 쪽, 상자 줄이 이미 제목 표 아래에서 시작한 쪽)만 되살렸다. 0014는 HWPX의 줄표 없는 쪽 번호를 상위가 고쳐서(#7633) 엔진 호출 둘만 남았다. 0021은 넷 가운데 (4)를 뺐다. 상위의 빈 개체 뒤 흐름 처리가 같은 자리를 다시 옮겨 효과가 없었다. 0025는 상위가 맞추지 못한 규칙 셋만 남았다. 0028은 (1)과 (2)의 절반을 뺐다. 상위 시험(`issue_6950`, `issue_6718`)을 깨뜨렸기 때문이다.
  - 0026은 상위가 같은 일(#8120, 시작하는 칸이 없는 행 빼기)을 하지만, 셀 영역 경계가 그 행에 걸리면 HWPX 저장을 통째로 거절한다. 0.8.7 앱은 그런 문서를 저장했으므로 그 경우만 0026처럼 영역을 위 행으로 넓혀 저장하는 패치로 바꿨다(`0026-hwpx-cellzone-on-dropped-rows`). 칸과 글은 그대로이고 영역의 테두리·배경만 넓어진다.
  - 0018(메모)은 상위의 구역 끝 보존(#7908)에 맞춰 다시 엮었다. 메모 목록은 모델에서 쓰고, 원본 바이트로 지키는 것은 바탕쪽 목록뿐이다. 엔진 호출 다섯의 이름과 주고받는 값은 그대로다.
- **편집기 패치는 35개에서 33개로 줄었다.** 글꼴 치환 기억(`studio-font-memo-state`, `studio-font-memo-use`, 결정 0054)은 상위의 `CanvasFontResolutionScope`(#7897)가 같은 일을 해서 뺐다. 표 안의 표 잘라내기와 빠른 교정은 바뀐 상위 코드에 맞춰 찾을 글을 고쳤다.
- **상위 편집기의 AI 도우미는 빌드에서 뺀다(`__RHWP_AI__: false`).** `devel` 편집기에는 제공자 SDK로 AI를 부르는 도우미가 들어 있다. 이 앱에서 AI로 가는 길은 앱의 AI 창 하나다(`docs/security.md`). 이 값이 `false`면 도우미 코드가 결과물에 남지 않는다. 결과물의 바깥 주소는 0.8.7 빌드와 같다(꺼 둔 글꼴 CDN 목록뿐).
- **편집기 빌드가 받는 소스를 넓혔다.** `devel` 편집기가 `rhwp-studio` 밖에서 읽는 것(`rhwp-shared/`, `assets/fonts/enclosed-pua-metrics.json`, `src/renderer/square_gradient.sksl`)을 더 받는다. 글꼴 파일은 여전히 받지 않는다. `rhwp-shared`의 PDF 가져오기 작업자가 저장소 자리로 엔진을 찾는 것(`../../pkg/rhwp.js`)은 빌드가 `vendor/rhwp-core`로 잇는다.
- 편집기 SDK(`@rhwp/editor`)는 npm 0.8.7을 그대로 쓴다. `devel`의 SDK는 기능을 더하기만 했고, 앱이 쓰는 메시지 형식은 같다.

## 택하지 않은 것

- **0.9.0 배포판을 기다린다.** 2026-10-23의 결정이었다. 저장소 주인이 바꿨다.
- **병합된 PR을 골라 `v0.8.7`에 옮긴다.** 통합 PR(#7882, #8148, #8228, #8319, #8348 등)이 서로 기대어 있어 하나씩 옮기면 충돌이 크고, 배포판이 나오면 모두 버려야 한다.
- **`devel` 끝을 날마다 따라간다.** 상위는 하루에도 여러 번 바꾼다. 커밋 하나에 고정하고, 옮길 때마다 아래 확인을 다시 한다.
- **상위가 바꾼 규칙(0007, 0028 일부)을 우리 패치로 되돌린다.** 상위가 한컴 인쇄본이나 자기 시험으로 확인한 규칙이고, 되돌리면 상위 시험이 깨진다. 남는 차이는 상위에 알릴 일이다.

## 결과

- 사용자 교재 묶음(공유하지 않는 문서, `F:\ieum-scratch\hwpx-overlap`)을 고치기 전 `devel`, 지금 앱 엔진(0.8.7-ieum.17), 새 엔진으로 견줬다.

  | 문서                                         | 쪽 수(devel / 지금 앱 / 새 엔진) | 본문 겹침(같은 순서) |
  | -------------------------------------------- | -------------------------------- | -------------------- |
  | 교재 초안 HWPX                               | 184 / 185 / 185                  | 19 / 1 / 8           |
  | 국어과 최종안 HWP·HWPX                       | 200 / 201 / 200                  | 15 / 1 / 1           |
  | 최종안을 한컴이 다시 저장한 HWPX(한글 198쪽) | 198 / 198 / 198                  | 15 / 3 / 1           |
  | 강사 가이드북 HWP                            | 181 / 182 / 181                  | 1 / 0 / 1            |
  | 모듈 5 교재                                  | 32 / 33 / 32                     | 4 / 0 / 0            |
  | 문서 도구가 만든 양식(한글 1쪽)              | 2 / 1 / 2                        | 0 / 0 / 0            |
  - 나아진 것: 한컴이 다시 저장한 최종안의 겹침이 3곳에서 1곳으로 줄었다. 최종안 HWP의 쪽 수가 201쪽에서 200쪽으로 한글(198쪽)에 가까워졌다.
  - 나빠진 것: 교재 초안의 겹침이 1곳에서 8곳으로 늘었다(가장 큰 것은 177쪽, 표가 여섯 줄을 덮는다). 문서 도구가 만든 양식은 1쪽에서 2쪽이 된다. 강사 가이드북은 172쪽에 겹침이 하나 생긴다.
  - 새 엔진에 남은 겹침은 모두 `devel`에도 있는 것이다. 우리 패치가 만든 것은 없다. `findings.md`에 적었다.

- 0028과 0021(4)를 뺀 자리에는 작은 차이가 남는다. 문단 기준 표 뒤 다음 줄이 한글보다 4px 아래, 문서 도구가 만든 양식의 셋째 표가 한글보다 5.5px 아래에 놓인다. 두 시험(`engine-layout.test.ts`, `engine-table-look.test.ts`)은 지금 값을 적고 한글 값을 주석으로 남겼다.
- 앱 시험(한글 편집기 1,195개, 한글 파일 읽기 307개, 터미널 명령어의 한글 시험)이 통과한다. 새 엔진에 맞춰 바꾼 시험과 그 까닭:
  - `.hwp`를 저장할 때 바꾼 구역의 바탕쪽 목록을 엔진이 스스로 지킨다(#7908). `section-tails.ts`는 이제 붙일 것이 없다. 수식 캡션(결정 0028)과 바탕쪽을 지키지 않는 엔진을 위해 그대로 둔다(`section-tails.test.ts`, `recovery-main.test.ts`).
  - 다시 연 엔진은 저장 줄이 없거나 합성한 줄의 탭을 저장된 폭이 아니라 문단의 탭 위치로 놓는다(상위가 인라인 개체 폭을 두 번 세지 않으려고 바꿨다). 새로 친 탭은 여전히 폭 없이 저장되므로 앱이 폭을 써 넣는 일(결정 0026)은 그대로 필요하다(`tab-widths.test.ts`).
  - HTML로 붙여 넣은 표가 표 바깥 여백만큼 좁다(본문 폭 567px → 칸마다 186.5px). 칸 하나 크기 바꾸기는 같은 단계(3.75px)로 움직인다(`engine-table-resize.test.ts`).
  - 시작하는 칸이 없는 행을 뺀 HWPX에는 원래 행 격자를 적은 곁 파일 `META-INF/rhwp-table-row-grids.json`이 들어가고, rhwp로 다시 열면 원래 행 수로 돌아온다. 한컴이 읽는 XML은 0.8.7 앱과 같은 2행이다(`engine-hwpx-merged-rows.test.ts`).
  - 밝기·대비는 그림 픽셀에 구워 넣는다(SVG 필터 없음, 회색 214·116, 한글 213·115). 0024 덕분에 반투명은 워터마크 그림만이다(`engine-picture-effect.test.ts`).
  - 각주 구분선 색이 `none`인 문서는 구분선을 그리지 않는다(0.8.7은 검은 선을 그렸다, `engine-layout.test.ts`).
  - 메모가 없는 문서는 메모 패치 유무와 상관없이 같은 바이트로 저장한다. 기준 해시를 메모 패치가 없는 `devel` 빌드의 것으로 바꿨다(`engine-memos.test.ts`).
  - 상위 편집기의 PDF 가져오기 대화상자는 다른 대화상자와 같은 틀 규칙을 쓴다(`dialog-theme.test.ts`).
- 엔진 WASM이 약 11.8MB에서 26.3MB로 커졌다. 상위 기본 기능에 PDF 가져오기(JBIG2·JPEG 2000·ICC 포함)가 들어갔기 때문이다. 설치본과 한글 탭마다 그만큼 더 든다. WASM에 링크된 Rust 크레이트는 224개이고 모두 허용형 라이선스다(제3자 고지 생성기로 확인).
- 사람이 확인할 것: 한컴 한글 2024로 (1) 곁 파일이 든 HWPX와 새 엔진으로 저장한 HWP·HWPX를 열고, (2) 각주 구분선 색이 `none`인 문서의 인쇄본에 구분선이 있는지 보고, (3) 빌드한 앱에서 한글 탭의 편집·저장·메모·한컴 단축키가 그대로인지 본다.
- 상위 엔진 시험: 고친 영역의 회귀 묶음 28개(시험 543개)와 메모·표·스타일·쪽 번호 단위 시험이 통과한다. 상위 시험 둘을 우리 동작에 맞게 바꿨다. 셀 영역 거절 사례는 저장되는지 보는 시험으로 옮겼고, 메모 앵커를 지운 문서의 저장은 이제 성공한다.
- 0.9.0이 나오면 이 고정을 태그로 바꾸고(`branch`를 지운다), 그 판이 담은 패치를 지운다. 결정 0050의 다른 내용(패치를 얹어 빌드하는 방식, 저장 바이트를 바꾸는 패치의 허락)은 그대로다.
