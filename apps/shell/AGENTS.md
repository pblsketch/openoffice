# apps/shell (`@genoffice/shell`)

실제로 배포되는 앱이다. Electron 프로세스 하나, 창 하나에 홈 화면과 에디터들을 탭(`WebContentsView`)으로 띄운다. 설치 프로그램에 들어가는 것은 이 앱뿐이고, 에디터들의 메인 프로세스 코드는 이 앱의 메인 번들 안에서 돈다.

## 맡은 범위

- 앱의 수명 주기(`src/main/index.ts`): 단일 인스턴스 잠금, userData 위치, 확장자에 따른 파일 라우팅, 탭별 메뉴 전환, 종료 처리, `--headless-export` 진입.
- 탭과 창: `src/main/tab-manager.ts`, 떼어 낸 창(`detached-windows.ts`), 닫기 확인(`window-close-guard.ts`), 렌더러 자원 감시(`renderer-watchdog.ts`), 닫은 워드 탭·창의 렌더러 프로세스 끝내기(`renderer-disposal.ts`), 크래시 기록과 알림(`crash-log.ts`, `crash-watch.ts`).
- 화면 나누기(분할 뷰, 결정 0037): 탭 관리자의 두 칸(가장자리로 끌어다 놓기와 오른쪽 클릭 메뉴로 나누기·풀기, 구분선으로 비율 바꾸기·반반·한쪽 닫기), 초점이 있는 칸에 따르는 AI 창 하나의 배선, 나눈 모습의 기억과 파일 지정 없는 실행에서의 복원(`src/main/split-memory.ts`). 화면과 뒷단이 주고받는 계약은 `src/shared/split-view-api.ts`, 껍데기와 편집기 화면 사이의 다리는 `packages/electron-utils/src/split-pane-bridge.ts`가 정한다.
- 홈 화면과 설정(`src/renderer/src/`): `Home.tsx`, `Onboarding.tsx`, `SettingsModal.tsx`, AI 설정 `SettingsAiSection.tsx`·`settings-ai.ts`(비공개 GitHub 읽기용 토큰 입력란 `set-read-url-token`, `readUrlGithubToken`·`withReadUrlGithubToken`), 통합 탭 `IntegrationsPane.tsx`, 별표 파일에 묻는 `KbAskPanel.tsx`, 앱 안 도움말(`i18n/help/`).
- 의견 보내기(결정 0036, `src/main/feedback.ts`): 도움말 메뉴와 설정 → 정보의 같은 입구 하나. 제품 버전·운영체제·화면 언어를 대화 상자에 보여 주고 클립보드에 복사한 뒤 Google 설문을 브라우저로 연다. 문구는 `feedback.ts`의 21개 언어 표, 모든 탭의 도움말 메뉴에 끼워 넣는 일은 `withHelpItems`, 채널은 `home:open-feedback-survey`다.
- 파일 색인과 지식 기반(`src/main/file-index/`, `knowledge-base.ts`), 최근 파일, 폴더 트리. 홈의 질문을 별표 그룹 하나로 좁히는 일(`knowledge-base.ts`의 `KbRunScopes`, `kb:open-scope`·`kb:close-scope`).
- 문서로 새 문서 만들기(`src/main/generate/`): 만들기 창(`generate-window.ts`, 화면은 `src/renderer/generate.html`과 `src/renderer/src/generate/`), 창 하나의 상태와 동작(`session.ts`), 요청 검사(`request.ts`), 자료의 상태와 글 길이(`materials.ts`), 자료가 열린 탭과 그 저장(`open-materials.ts`), AI 없이 바꾸기(`convert.ts`, `converted-tab.ts`), 조정 가능한 값(`limits.ts`). 홈의 입구는 `generate:open-with-paths`·`generate:open-with-group`이다.
- PDF 도구 창(`src/main/pdf-tools/`, 결정 0030): 창과 대화 상자·저장(`pdf-tools-window.ts`), Electron 없이 도는 처리(`tools.ts`), 화면은 `src/renderer/pdf-tools.html`과 `src/renderer/src/pdf-tools/`, 문구는 `i18n/pdf-tools/`(도구 이름은 PDF 편집기 리본의 문구를 복사). 홈의 입구는 "PDF 도구" 카드와 `pdf-tools:open`이다.
- 출처 기록(`document-links.ts`, 껍데기 쪽 배선 `document-links-shell.ts`)과 모든 에디터의 파일 메뉴에 붙는 "이 문서로 다른 문서 만들기"·"자료 보기"·"이 문서로 만든 문서"(`document-links-menu.ts`).
- 열린 탭 가운데 저장하지 않은 문서의 목록을 에디터 뒷단에 알려 주는 일(`index.ts`에서 `setOpenFilesSource`).
- 자동 업데이트(`updater.ts`, `update-window.ts`, `update-resume.ts`, `update-notes.ts`)와 패키징 설정 `electron-builder.cjs`. 릴리스 본문을 안전한 텍스트 블록으로 바꿔 창에 보여 주는 설계는 `docs/plans/update-details.md`에 있다.
- 외부에서 들어오는 입구: 앱 안 MCP 서버(`src/main/mcp/`), 명령줄용 제어 채널(`control-server.ts`), 열린 문서 목록 게시(`open-documents.ts`), 명령줄 PATH 연결과 실행기 위치 기록(`cli-link.ts`), 스킬·MCP 등록 IPC(`integrations-ipc.ts`).
- 기본 앱 등록과 파일 연결(`default-app.ts`), 설치 프로그램이 하는 Windows 등록(`build/installer.nsh`: PATH, 탐색기 "새로 만들기" 서식, `.odt`의 "연결 프로그램" 후보).
- PDF 구조 작업과 보관소 채널(`src/main/pdf-structure-ipc.ts`, 로직은 `src/main/pdf-structure/`): PDF 편집기의 `structure*`·`store*` 채널을 등록하고, 구조 작업마다 Electron `utilityProcess`를 하나 띄운다(`runner.ts`, 진입점 `pdf-structure-process.ts`). 앱 안 저장 뒤 끝나지 않은 작업 기록 옮기기(`job-migration.ts`, 다섯 작업 종류), 출력 형식별 끼움 자리(`plugins.ts`)도 여기 있다. PDF 읽기 도우미(결정 0043)의 보관소 읽기·쓰기(카드, 핵심 표시, 개요, 고친 번역, 페이지 지문 목록, 지우기 확인의 수)도 `pdf-structure/handlers.ts`가 받는다. 그 창에 열린 파일에서 셸이 계산한 해시만 받는 규칙은 같다.
- PDF마다 노트의 셸 쪽(`src/main/pdf-note-tabs.ts`, 결정 0043): `configurePdfRuntime`에 `openNote`·`insertIntoNote`를 주입한다. PDF 편집기 메인이 정한 노트 경로(저장 창으로 고른 것이나 `note-links.json`에서 읽은 것)를 받아, 다시 실제로 있는 절대 경로의 `.md` 파일인지 보고, 그 노트의 마크다운 탭이나 떼어 낸 창을 앞으로 가져오거나 새 마크다운 탭으로 연다. 넣을 글은 그 탭의 webContents에 맡기고(`queueMarkdownNoteAppendFor`), 마크다운 편집기가 문서 끝에 넣는다. 셸은 노트 파일에 쓰지 않는다.
- 에이전트 창(결정 0032, `src/main/agent/`): 창과 채널(`agent-window.ts`), 세션 관리와 폴더·지시문(`agent-sessions.ts`), 세션 전용 MCP 서버와 그 도구(`agent-mcp.ts`). 화면은 `src/renderer/agent.html`과 `src/renderer/src/agent/`, preload는 `src/preload/agent.ts`, 문구는 `i18n/strings-agent.ts`와 `i18n/agent/<언어>.ts`. 홈의 입구는 `home:open-agent-window` 하나다.
- Google 드라이브(결정 0033, `src/main/drive/`): 연결과 창구(`drive-ipc.ts`), 갱신 토큰의 암호화 보관(`drive-vault.ts`), 연 파일의 PC 사본과 저장 뒤 올리기(`drive-files.ts`), 편집기 AI의 검색·읽기(`drive-ai.ts`), AI 창 첨부용 고르기 창과 내려받기(`drive-picker-window.ts`, `drive-attach.ts`, 화면은 `src/renderer/drive-picker.html`과 `src/renderer/src/drive-picker/`, preload `src/preload/drive-picker.ts`), 브라우저 페이지와 대화 상자 문구(`drive-strings.ts`). 홈과 고르기 창이 같이 쓰는 목록은 `DriveBrowser.tsx`, 화면은 홈의 `DrivePanel.tsx`와 설정 → 연동의 `DriveSettingsCard.tsx`, 문구는 `i18n/strings-drive.ts`와 `i18n/drive/<언어>.ts`, preload는 `window.aiOfficeDrive`다. Google 클라이언트는 빌드 때 `__GENOFFICE_GOOGLE_CLIENT_ID__`로 들어오고, 없으면 상태가 `unavailable`이라 아무 데도 나오지 않는다.
- EPUB 편집기 탭(결정 0066): 마인드맵 편집기와 같은 자리에 붙였다. 확장자 판정(`app-routing.ts`의 `EPUB_RE`), 실행 인자(`launch-paths.ts`), 끌어다 놓기, 폴더 나무·파일 색인(`TREE_FILE_EXTENSIONS`), 탭 종류 `epub`(`tab-manager.ts`의 `openEpubTab`·`findEpubTabByPath`, 바뀜 상태, 닫기 확인, 다시 열기), 떼어 낸 창, 메뉴(`index.ts`의 `buildEpubMenu`: 파일의 열기·홈·저장·다른 이름으로 저장·책 번역·닫기, 편집의 되돌리기·다시 하기·찾기·바꾸기, 보기의 확대. 편집·보기 항목의 단축키는 메뉴에 보이기만 하고(`registerAccelerator: false`) 편집기 화면이 직접 받는다), 열기 창 필터(`filterEpub`), 홈의 지원 형식 글·필터·아이콘(새 책 타일은 없다), 탭 아이콘, 드라이브 목록, `epub-asset://` 등록(특권 스킴은 `registerPrivilegedSchemes` 한 번에 함께), 앱 안 MCP의 열린 책 읽기·저장(`kind: "epub"`, `epubReadText`·`epubSaveToPath`), 패키징 모듈 폴더(`modules/epub`). 편집기에는 `configureEpubRuntime`으로 데이터 폴더, 작업 기록 옮기기, "열린 탭인가" 검사를 넘긴다.
- 설정 → 일반의 "AI 결과 보관소" 줄(`SettingsResultStore.tsx`): `<userData>/pdf-store`가 차지한 용량과 "모두 지우기". PDF의 AI 결과와 EPUB 책 번역이 함께 들어 있다. 폴더 이름(`pdf-store`)은 바꾸지 않는다. 채널은 `result-store-ipc.ts`, preload는 `window.aiOfficeResultStore`다.
- 빠른 미리보기(`src/main/quick-look/`): 홈 파일 목록과 Windows 파일 탐색기·바탕화면에서 스페이스바(`Space`)로 문서를 바로 훑어보는 기능. 내장 썸네일과 구조화된 본문 추출(`extract.ts`), 독립 미리보기 창과 시스템 트레이 유지(`quick-look-window.ts`), Windows 탐색기 스페이스바 도우미(`win-quicklook.cs`, `build-win.mjs`, `win-explorer-hook.ts`), 화면 부품(`src/renderer/quick-look.html`, `src/renderer/src/quick-look/`), 설정 줄(`SettingsQuickLook.tsx`), 21개 언어 문구(`i18n/strings-quick-look.ts`, `i18n/quick-look/`).
- 이음오피스 문서에서 첨부(결정 0035, `src/main/doc-picker/`): 편집기 AI 창의 첨부 부탁에 답해 문서 고르기 창을 띄운다. 목록 만들기(`doc-list.ts`), 창과 식별자 검사(`doc-picker-window.ts`, `MAX_PICKS` 20), 화면은 `src/renderer/doc-picker.html`과 `src/renderer/src/doc-picker/`, preload는 `src/preload/doc-picker.ts`(`window.aiOfficeDocPicker`), 문구는 `i18n/strings-doc-picker.ts`와 `i18n/doc-picker/<언어>.ts`. `src/main/index.ts`가 `doc:attach-available`(껍데기 앱이 있으면 참), `doc:pick-attachments`(부탁한 창 위에 고르기 창을 띄움), `doc:attach-list`(입력란 `@` 목록, 결정 0051)를 등록하고, 열린 탭·떼어 낸 창과 최근 파일을 묻는 편집기 기준의 목록(옆 칸 → 열린 문서 → 최근, 지금 문서 제외)으로 만든다. `@` 목록에서는 없어진 최근 파일을 뺀다(`toMentionItems`). 채널 이름과 모양은 `src/shared/doc-picker-api.ts`가 정한다.
- 사용자 스킬(결정 0048, `src/main/user-skills/`): 출처를 읽고 상태를 저장하는 창구(`user-skills-service.ts`, `user-skills-ipc.ts`, 켜기·끄기와 가져오기·설치·업데이트·내보내기·지우기는 메인 창의 요청만 받음), 기본 스킬 폴더 위치(`builtin-dir.ts`, 설치본은 `resources/builtin-skills`), 양식 사본과 양식 미리보기 탭(`template-tabs.ts`, `template-tabs-ipc.ts`). 화면은 설정 → 스킬(`src/renderer/src/skills/`, 문구 `i18n/skills/<언어>.ts`, 도움말 링크는 도움말의 `skills` 주제를 연다)이다.
- 에이전트 창의 스킬과 웹(결정 0049): 세션에 실을 스킬과 양식 후보(`src/main/agent/agent-skills.ts`), 스킬 카드·설치 제안(`AgentSkillCard.tsx`, `AgentInstallProposal.tsx`), Codex 웹 검색·명령의 인터넷 접속의 시작 화면 선택과 Claude 웹 허락 표시(`renderer/src/agent/agent-web.ts`, 문구 `i18n/agent-web/`; 프로젝트 폴더별 기억은 `main/app-settings.ts`의 `agentProjectPrefs`를 `agent-window.ts`가 읽고 쓴다). 스킬을 바꾸는 IPC는 메인 창에서 온 요청만 받는데(`canManage`), 에이전트 창에는 깃허브 설치 미리보기에 필요한 `importGitHub`·`cancelImport`·`install` 셋만 더 열려 있다, 이전 사용자 한 번 안내(`i18n/agent-skills/`).

## 맡지 않는 것 (경계)

- 문서 편집과 형식별 저장·내보내기는 이 모듈의 범위가 아니다. 각 에디터(`apps/docs`, `apps/sheets`, `apps/slides`, `apps/pdf`, `apps/markdown`, `apps/html`, `apps/mindmap`, `apps/hwp`, `apps/epub`)가 한다. shell은 그 메인 모듈의 내보낸 함수(`createDocsView`, `configureSheetsRuntime` 등)를 부른다.
- AI 요청의 실행은 범위가 아니다. `ai:*` 채널과 구독 IPC 채널은 `apps/docs/src/main/docs-main.ts`의 `registerAiIpc`가 등록한다. shell은 그것을 한 번 호출할 뿐이고, AI와 관련해 직접 응답하는 채널은 `home:open-subscription-install-help`(벤더의 설치 안내 페이지 열기)와 `ai:open-model-settings`(홈 탭의 설정 화면 열기)뿐이다.
- 제공자 선택 규칙, 구독 프로그램 실행은 `packages/ai-provider`, 연결 카드와 알림 컴포넌트는 `packages/ui`의 범위다.
- 새 문서의 글을 쓰는 것은 만들 문서 쪽 에디터(PPT, HTML, 마인드맵)의 AI다. 이 모듈은 생성 코드를 갖지 않고, 요청을 새 탭 앞으로 맡겨 둘 뿐이다. 맡겨 두는 곳은 `packages/electron-utils`의 `generate-handoff.ts`이고(`src/main/generate/handoff.ts`는 그것을 다시 내보낸다), 가져가는 창구(`<에디터>:handoff-take`)는 각 에디터가 등록한다.
- 파일을 글로 읽는 일과 가리기 적용은 `packages/file-parse`, 지도 파일의 해석과 개요 글은 `packages/xmind-engine`, EPUB 책의 해석·저장·번역 결과는 `packages/epub-engine`의 범위다. 책 번역 작업은 EPUB 편집기 화면 안에서 돌고, 셸은 끝나지 않은 작업 기록 옮기기(`job-migration.ts`)만 빌려준다.
- 명령줄과 그 MCP 서버의 구현은 `packages/cli`의 범위다. 앱 안 MCP 서버의 창 없는 도구들은 그 명령줄을 프로세스로 실행해 결과 봉투를 옮길 뿐, 문서 엔진을 다시 구현하지 않는다(`src/main/mcp/cli-runner.ts`).
- 제품 이름과 저장소 좌표의 정의는 `packages/i18n/src/product.ts`의 범위다.

## 항상 지켜야 하는 것

- 구독 프로그램을 끝내는 책임은 이 프로세스에 있다. `src/main/index.ts`는 `app.whenReady` 뒤 userData 경로가 확정된 다음 `initSubscriptionChildTracking(app.getPath('userData'))`를 한 번 부르고(강제 종료된 이전 실행이 남긴 프로세스를 정리하고 이번 실행의 기록을 시작한다), `will-quit`와 `process.on('exit')` 양쪽에서 `shutdownSubscriptionChildren()`을 부른다. `app.exit()`·`process.exit()`은 `will-quit`를 건너뛰므로(headless 내보내기가 그렇게 끝난다) 둘 중 하나만으로는 부족하다. 에디터 코드에서 `initSubscriptionChildTracking`을 또 부르지 않는다.
- 구독 IPC 채널(`SUBSCRIPTION_IPC_CHANNELS`)을 shell에서 등록하지 않는다. 같은 채널을 두 번 등록하면 예외가 난다. preload는 채널 이름과 판독 함수를 `@genoffice/ai-provider/browser`에서 가져와 `window.aiOfficeSubscription`으로 내보낸다. 핸들러가 없으면 상태는 `checking`으로 읽힌다. 로그아웃(`ai:subscription-logout`)을 내보내는 preload는 이 앱의 것뿐이다. 에디터의 preload에 넣지 않는다(`tests/preload-subscription.test.ts`가 지킨다).
- 드라이브의 토큰은 뒷단 밖으로 나가지 않는다. 드라이브 창구는 상태, 파일 목록, 파일 id만 주고받는다. 드라이브에 쓰는 길은 `drive-files.ts`의 저장 뒤 올리기 하나이고, AI 창구(`drive:ai-*`)는 읽기만 한다. 드라이브 창구와 preload 멤버의 이름에 `cloud`·`account`를 쓰지 않는다(`tests/removed-features.test.ts`).
- 계정 바꾸기와 로그아웃은 확인을 받은 뒤에만 실행한다. 둘 다 벤더 프로그램 자신의 명령이고 이 PC 전체에 적용되어, 터미널에서 쓰는 같은 프로그램도 함께 바뀐다. 설정 화면은 프로그램 이름과 이 사실을 적은 확인(`setSubLogoutConfirm`, `setSubSwitchConfirm`)을 카드 아래에 띄우고, 확인 버튼을 눌렀을 때만 `connection.logout`·`connection.switchAccount`를 부른다. 확인 없이 이 둘을 부르는 경로를 만들지 않는다. 버튼은 설정의 카드에만 있고 첫 실행 안내와 홈의 질문 패널에는 없다.
- 로그인된 계정(이메일)은 설정 → AI의 카드에만 그린다. 계정 구역의 요약 줄에도, 다른 화면에도 넣지 않는다. 저장하거나 기록에 남기지 않는다.
- **의견 보내기는 세 줄만 보여 주고 복사한 뒤 설문을 연다.** 화면에 보이는 것도, 클립보드에 들어가는 것도 제품 버전·운영체제·화면 언어뿐이다. 문서 내용·경로·파일 이름·열린 탭·계정·크래시 기록은 넣지 않는다. 앱이 스스로 보내는 것은 없고, 여는 곳은 `src/main/feedback.ts`의 `FEEDBACK_SURVEY_URL` 하나뿐이다. 그 값은 저장소 주인이 게시한 설문 주소이며, 설문 항목을 고쳐도 주소는 그대로다. `tests/feedback.test.ts`가 지킨다.
- preload는 로그인·설치 실패의 원문 오류를 렌더러에 넘기지 않는다(`subscriptionLaunchResultOf`). 실행 파일 경로가 들어 있을 수 있어서다. 화면은 번역된 일반 문장을 쓴다.
- PC에 등록되는 이름은 이 제품의 것이고 원본 GenOffice와 겹치지 않는다. 앱 id `io.github.pblsketch.ieumoffice`, 제품 이름 `IeumOffice`, 패키징된 앱 이름 `ieumoffice`(업데이트 캐시 폴더 이름이 여기서 나온다), userData는 설치본 `<appData>/IeumOffice`, 패키징되지 않은 실행 `<appData>/IeumOffice-Dev`다. 원본 앱의 프로필 폴더를 물려받거나 읽지 않는다. `electron-builder.cjs`의 상수, `package.json`의 `productName`, `packages/i18n`의 상수는 서로 같아야 한다.
- 원본이 PC에 등록한 것(`genoffice` 명령, `~/.genoffice`, 원본의 MCP 항목과 스킬 폴더)은 건드리지 않는다. 실행기 위치 기록은 `~/.ieumoffice/launcher`에만 쓴다.
- 패키징되지 않은 실행은 설치본과 userData·단일 인스턴스 잠금을 공유하지 않는다. 공유하면 개발 실행이 조용히 종료되면서 인자를 설치된 앱으로 넘겨 버린다. 테스트 드라이버는 `GENOFFICE_USER_DATA`로 임시 폴더를 지정한다.
- headless 진입은 모듈 최상위에서 처리한다. `parseHeadlessExportArgv`와 `setHeadlessMode(true)`가 에디터 모듈이 무엇이든 등록하기 전에 실행되어야 한다. 구독 상태 확인은 첫 `statuses` 요청 때 시작하므로 headless 실행은 벤더 프로그램을 띄우지 않는다. 이 순서를 깨는 "시작 시 미리 확인"을 넣지 않는다.
- 업데이트는 이 제품의 공개 저장소의 GitHub Releases에서만 받는다. 저장소는 `electron-builder.cjs`의 `publish`에서 `app-update.yml`로 구워지고, 빌드 시 주입되는 값이나 토큰이 없다. 확인 실패(릴리스 없음, 네트워크 없음)는 조용히 넘긴다. 설치 프로그램은 서명하지 않는다.
- **업데이트 창의 릴리스 본문은 원격 글이다.** `update-notes.ts`가 HTML을 블록으로 바꾼 것만 그리고, 화면 조립은 `createElement`/`textContent`로만 한다(`innerHTML` 금지). 그림·스크립트·스타일·링크 주소는 버리고, 원문·결과·섹션에 상한을 둔다. 새 네트워크 요청을 만들지 않고(기존 피드 요청에 얹힌다) 본문을 저장하거나 보내지 않는다. `tests/update-notes.test.ts`가 지킨다.
- 앱 안 MCP 서버와 제어 채널은 로컬 전용이다. MCP 서버는 루프백에만 바인드하고 Host 헤더를 검사한다(인증이 없으므로). 제어 채널은 userData의 소켓·명명된 파이프와 실행마다 새로 만든 토큰을 쓰고, 명령은 "이 위치를 보여 줘"와 "선택을 읽어 줘"뿐이다. 요청으로 파일을 쓰거나 코드를 실행하는 명령을 추가하지 않는다.
- 스킬과 MCP 등록은 통합 탭에서 사용자가 누를 때만 쓴다. 시작 시 자동으로 에이전트 설정 파일을 고치지 않는다.
- **만들기 창은 AI 실행을 시작하지 않는다.** "만들기"는 만들 종류의 제목 없는 새 탭을 열고 그 탭의 webContents 앞으로 요청을 한 번 맡겨 둘 뿐이다. 실행은 그 탭의 에디터가 자기 보내기 판단을 지나 시작한다. 탭이 열렸다는 이유만으로 실행하는 길을 만들지 않는다. "만들기"를 누르면 뒷단이 요청과 자료를 창의 마지막 상태와 무관하게 다시 검사한다.
- **자료의 글은 `parseFileToText`로만 읽고, 길이만 남긴다.** 만들기 창은 알림용 길이를 재는 데만 글을 쓰고 그 자리에서 버린다. AI 없이 바꾸기도 자료를 `parseFileToText`로만 읽는다(가린 자리는 이름표). 마크다운 자료에 가린 부분이 있는지 알리는 판단(`markdownRedactionNotice`)만 파일의 원문과 견주고, 그 결과는 예/아니오뿐이다.
- **저장하지 않은 자료로는 만들지 않는다.** 어떤 탭에 열려 있고 저장하지 않은 변경이 있는 자료가 하나라도 있으면 만들기와 바꾸기를 막는다. 한 번도 저장하지 않은 문서는 자료가 될 수 없다. 마지막 저장본으로 진행하는 길을 만들지 않는다.
- **출처 기록은 문서 밖에만 쓴다.** `document-links.json`(userData)에만 적고 문서 파일에는 아무것도 넣지 않는다. 요청 글을 적지 않는다(읽는 이벤트에 글이 없고, 기록에도 그 칸이 없다). 기록은 넘겨받은 자료가 하나라도 붙은 실행이 그 탭에서 시작됐거나 바꾸기가 이루어졌고, 그 탭의 문서가 처음 저장됐을 때만 쓴다. 디스크에 없는 파일이라는 이유로 기록을 지우지 않는다.
- **그룹으로 좁힌 질문은 main이 지킨다.** 패널은 실행마다 그룹 이름 하나만 넘기고, main이 그 실행의 불투명한 범위 값을 만든다. `kb:*` 호출마다 main이 별표 저장소에서 그룹의 파일을 다시 구한다. 화면이 보낸 파일 목록을 믿지 않고, main이 갖고 있지 않은 범위 값은 거절한다(범위 없는 질문으로 읽지 않는다). 좁히기는 기존 검사(별표 파일만, 저장하지 않은 파일 거절, 디스크와 같은 색인의 발췌만)가 허락한 것을 더 거르기만 한다.
- **PC 밖으로 나가는 색인 발췌는 두 번 거른다.** 묻기의 검색과 재정렬은 색인이 디스크의 지금 파일과 같은 파일(`pathsIndexedAsOnDisk`)이면서 저장하지 않은 변경이 없는 파일(`withoutUnsavedFiles`)의 발췌만 쓴다. 색인 본문에 들어가는 것을 바꾸면 `file-index/store.ts`의 `EXTRACT_VERSION`을 올린다. 올리면 다음 실행 때 색인을 통째로 다시 만든다.
- **Windows 설치본은 `.xmind`·`.hwp`·`.hwpx`·`.epub`을 파일 연결(`fileAssociations`)로 등록하지 않는다**(`electron-builder.cjs`의 `WIN_OPEN_WITH_ONLY_EXTS`, `.txt`·`.json`과 같다). 설치가 사용자의 기본 프로그램을 가져가지 않게 하기 위해서다(마인드맵과 전자책은 지금 열던 프로그램, 한글 문서는 한컴오피스). 대신 "연결 프로그램"에만 후보로 넣는다(아래 `.odt` 항목과 같은 방식). `build/installer.nsh`가 제품 전용 ProgId(`IeumOffice.HWPDocument`·`IeumOffice.HWPXDocument`·`IeumOffice.MindMap`·`IeumOffice.EPUBBook`)를 `DefaultIcon`과 함께 쓰고 `Software\Classes\.<확장자>\OpenWithProgids` 값 하나만 남긴다. 기본값(`.hwp`·`.hwpx`·`.xmind`·`.epub`의 `""`)은 쓰지 않고, 제거할 때 자기 값과 자기 ProgId만 지운다. 아이콘(`hwp.ico`·`mindmap.ico`·`epub.ico`)은 `electron-builder.cjs`의 `win.extraResources`로 `resources\`에 들어간다(electron-builder는 `win.fileAssociations`에 있는 형식의 아이콘만 넣으므로 이 넷은 따로 넣는다). macOS는 `.epub`을 대체 프로그램(`rank: Alternate`)으로만 올린다. `tests/open-with-icons.test.ts`가 이 배선을 지킨다.
- **Windows 기본 앱 목록에는 제품 이름과 능력(`Capabilities`)으로 오른다.** `build/installer.nsh`가 `Software\RegisteredApplications`에 `IeumOffice`를, `Software\IeumOffice\Capabilities\FileAssociations`에 확장자별 제품 ProgId를 쓴다. 이 등록은 기본 프로그램을 바꾸지 않는다. Windows 기본 앱에서 이음오피스를 고를 때 앱 실행 파일(`Applications\IeumOffice.exe`, 앱 로고)이 아니라 확장자별 ProgId(문서 아이콘)가 기록되게 하려는 것이다. 이 등록이 없으면 이전에 앱 이름으로 저장된 `.hwp` 선택이 앱 로고를, 나중에 고른 `.hwpx` 선택이 `hwp.ico`를 보여 주는 식으로 갈린다. 이미 저장된 선택은 설치만으로 바뀌지 않으니, 사용자가 Windows 설정에서 한 번 다시 골라야 한다. 제거할 때 `RegisteredApplications`의 자기 값과 `Capabilities` 키만 지운다.
- "GenOffice를 기반으로 합니다" 고지(문자열 키 `setBasedOn`, 값에 `{{GenOffice}}`)는 21개 언어 모두에 남긴다. 원본 이름이 화면에 나오는 곳은 이 한 줄뿐이어야 한다. 다른 문자열과 도움말 제목·본문에 `{{GenOffice}}`를 쓰면 `tests/product-identity.test.ts`가 실패한다.
- 없앤 기능(사용 통계 전송, 자체 계정 로그인, 클라우드 프로젝트 목록 등)의 모듈·IPC·호출부를 되살리지 않는다. `tests/removed-features.test.ts`가 지킨다. 원본의 변경을 병합할 때 특히 본다.
- **닫은 워드 탭·창의 webContents는 닫거나 파괴하지 않는다**(UI 멈춤 회피, `tab-manager.ts`의 주석). 대신 `teardownDocsRenderer` 뒤에 `releaseClosedRenderer`로 렌더러 프로세스만 끝낸다. 빠지면 닫을 때마다 약 215MB가 앱이 끝날 때까지 남는다. 다른 열린 화면과 프로세스를 함께 쓰면 끝내지 않는다.
- **크래시 기록(`<userData>/crash-log.jsonl`)에는 시각, 종류, 이유 낱말, 종료 코드, 편집기 종류와 메모리 숫자(앱 전체 사용량, PC의 남은·전체 메모리, 진행 중인 AI 요청 수, 떠 있는 구독 프로그램 수. 정수 MB와 개수만)만 들어간다.** AI 요청이 진행 중일 때 PC의 남은 메모리가 부족하면 `low-memory` 줄을 남긴다(`startLowMemoryWatch`, 10분에 한 번 이하). 기록만 하고 아무것도 멈추거나 미루지 않는다. 문서 내용, 제목, 경로, 파일 이름, URL, 오류 메시지를 넣지 않는다(`crashLine`이 허용한 칸만 쓰고, 경로처럼 보이는 값은 버린다). 64KB를 넘지 않고 밖으로 보내지 않는다. 크래시 덤프(`crashReporter`)는 문서 내용이 담길 수 있어 켜지 않는다. 메인 프로세스 예외는 `uncaughtExceptionMonitor`로만 받는다. `uncaughtException` 처리기를 붙이면 Electron의 기본 동작이 바뀐다.
- 앱 안 MCP는 대화 상자 없이 저장하므로 문서의 형식을 바꾸지 않는다. `save_session`은 세션 형식(docx)이 아닌 확장자, 특히 `.odt`를 거절하고 명령줄 `convert`를 쓰라고 안내한다(`withSaveExtension`). 열린 문서 목록은 워드 탭이 담은 형식(`format`: `docx`/`odt`)을 함께 보이고, `read_docx`는 `.odt`도 읽는다. 꺼 둔 기능과 보호된 칸의 거절은 편집기가 한다.
- `.odt`는 워드 문서다. 열기 판정(`app-routing.ts`의 `ODT_RE`, `index.ts`의 `routeDocumentPath`), 열기 창(`OPEN_DIALOG_EXTENSIONS`와 `index.ts`의 `filterOdt` 필터 이름), 끌어다 놓기(`packages/electron-utils`의 `drop-open.ts`), 명령줄 경로(`launch-paths.ts`), 폴더 트리·파일 색인(`TREE_FILE_EXTENSIONS`), 최근 파일과 홈의 형식 묶음(`EXT_FAMILY`, `SEARCH_EXT_FAMILY`, `Home.tsx`의 `FILTER_FAMILY`·`OPEN_LOCAL_EXTENSIONS`·`FILE_ICONS`), 앱 안 MCP의 형식 표(`mcp/tools/formats.ts`, `mcp` 부분의 저장은 docx만. 형식은 대화 상자 없이 바꾸지 않는다)가 모두 같은 답을 내야 한다. 하나를 고치면 나머지도 고친다(`tests/odt-shell-wiring.test.ts`). 새 문서의 기본 형식은 docx다. `.docx`↔`.odt` 이름 바꾸기는 막는다(내용이 바뀌지 않으므로 `renameStaysInApp`).
- `.odt`는 Windows "연결 프로그램" 후보로만 등록한다. electron-builder `fileAssociations`에 넣으면 NSIS가 `.odt`의 기본값을 써서 기본 프로그램을 가져가고, `WIN_OPEN_WITH_ONLY_EXTS`는 Windows 등록을 아예 뺀다. 그래서 `build/installer.nsh`가 제품 전용 ProgId `IeumOffice.OpenDocumentText`(열기 명령, 아이콘은 설치 프로그램이 두는 `resources\docx.ico`를 그대로 쓴다)와 `Software\Classes\.odt\OpenWithProgids`의 값 하나만 쓰고, 제거할 때 그 값과 ProgId만 지운다. `.odt` 키와 다른 프로그램의 값은 건드리지 않는다. `default-app.ts`의 기본 앱 목록에도 넣지 않는다(`tests/odt-open-with.test.ts`). 실제 등록은 설치본을 설치해 봐야 확인된다.
- 마크다운·HTML 탭 메뉴의 "ODT로 내보내기"(`menuExportOdt`)는 "Word로 내보내기" 바로 뒤에 있고 편집기에 `'odt'` 내보내기 요청을 보낸다. 워드 편집기의 메뉴는 `apps/docs`가 만들므로(`buildDocsMenu`), ODT 문서에서 꺼 두는 메뉴는 그쪽이 정한다.
- 모든 창은 `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`다. `shell.openExternal`은 `safeExternalUrl`을 거친 값만 받는다.
- 구조 작업은 셸 메인 프로세스에서 돌리지 않는다. 큰 문서에서 창이 멈추지 않도록 작업마다 별도 프로세스를 띄우고, 답했을 때, 실패했을 때, 화면이 취소했을 때, 그 탭(webContents)이 사라졌을 때, 앱이 끝날 때 프로세스를 끝낸다. 한 창이 동시에 돌리는 작업은 4개(`MAX_JOBS_PER_OWNER`)까지다. 기존 워드·PPT·엑셀 변환(`pdf2docx-local.ts` 등)은 예전처럼 메인에서 돈다. 이 경로는 바꾸지 않는다.
- 구조 작업과 보관소 채널은 화면이 보낸 경로를 믿지 않는다. 읽는 파일은 그 창에 허가된 파일(`pdfPathGranted`)이어야 하고, 쓰는 곳은 셸의 저장 창이 고른 대상(`structurePickTarget`, 작업 하나에 한 번)뿐이며 원본 파일은 쓸 수 없다. 보관소 읽기·쓰기는 셸이 그 창의 파일에서 계산한 문서 해시로만 받는다. 단독 실행처럼 채널이 없으면 화면은 `not-available`을 받는다.
- **PDF 도구 창은 경로를 화면에 넘기지 않는다.** 입력은 메인의 열기 대화 상자로만 고르고 화면에는 불투명한 id만 준다. 결과는 메인의 저장 대화 상자가 고른 곳에만 쓰며, 원본 파일이나 저장하지 않은 변경이 있는 채 열린 파일에는 쓰지 않는다. AI와 네트워크를 쓰지 않고, 처리는 편집기의 함수(`apps/pdf/src/main`의 `save-pdf.ts`, `images-to-pdf.ts`, `print-prep.ts`, `overlay.ts`, `annot-strip.ts`, `compress.ts`, `read-text.ts`)만 부른다. 용량 줄이기의 그림 처리는 `image-recode.ts`(크로미움 `nativeImage`)가 메인에서 한 장씩 한다(작업 프로세스에는 `nativeImage`가 없다). 빈 페이지 찾기는 페이지를 모두 그리므로 메인에서 돌리지 않고, `pdf-structure-ipc.ts`의 `runWindowJob`으로 구조 작업 프로세스(작업 종류 `blankPages`)에서 돌린다. 그 창이 닫히면 작업도 끝난다. 지우기는 그 찾기가 보여 준 페이지만 받는다. 암호 걸기·풀기와 파일 복구도 같은 작업 프로세스에서 돈다(작업 종류 `encrypt`, `decrypt`, `repair`, `tools.ts`의 `jobFor`). 암호는 그 작업에만 실어 보내고 로그에 쓰지 않으며, 결과는 메인이 다시 읽어 약속대로(암호를 묻는지, 다른 도구가 읽는지)인지 확인한 뒤에 저장 창을 띄운다. 암호가 걸린 PDF는 암호 풀기에만, pdf-lib가 읽지 못하는 PDF는 파일 복구에만 고를 수 있다(`toolAccepts`, 창의 `pagesFor`). PDF 편집기 리본의 "PDF 도구" 메뉴는 `configurePdfRuntime`의 `openPdfTools` → `openPdfToolsWithFile`로 들어온다. 파일은 대화 상자로 고른 것과 같은 검사(`inputsFrom`)를 거치고, 창은 기다리는 작업을 한 번만 가져간다(`pdf-tools:take-start`). 배경 겹치기의 배경 PDF는 입력 목록과 따로 고른 id(`backgroundId`)로 받고, 원본 검사에 함께 든다. 그림을 받는 도구(이미지로 PDF 만들기)에는 그림으로 고른 입력만, PDF 도구에는 PDF로 고른 입력만 들어간다(`input.kind`). 결과 열기는 `openGeneratedDocument`(같은 경로의 PDF 탭은 다시 읽음), 편집기로 넘기는 카드는 `openDocumentPath`(열린 탭은 앞으로만)를 쓴다.
- 보관소의 "모두 지우기"는 설정 화면에서 확인을 받은 뒤에만 부른다. 도는 작업이 있는지는 보지 않는다(그 작업은 이후 항목을 다시 쓴다).
- **문서 고르기 창은 방금 건넨 목록에 있는 것만 받는다.** 저장된 문서의 식별자는 그 경로다(경로를 감추는 것은 보호가 아니다 — 편집기 화면은 이미 아무 경로나 첨부로 읽게 할 수 있다, 결정 0051). 껍데기 앱은 방금 창에 건넨 목록에서 고를 수 있는 상태(`ok`)인 식별자일 때만(정해진 길이 상한 안에서) 받아들여 그 경로를 편집기로 돌려준다. `modified`(저장 안 된 변경)와 `unsaved`(저장 안 한 문서)는 고를 수 없다. 묻는 편집기(`doc-asker.ts`의 `resolveDocAsker`: 창 안 탭 → 떼어 낸 창, 못 찾으면 빼는 것 없이)는 고르기 창을 띄울 때 정해 창이 떠 있는 동안 유지한다. 목록을 만들 때도 형식과 크기만 보고 파일 내용은 읽지 않는다. 고르기 창은 한 번에 하나이고, 창을 닫으면 취소다. 새 창을 이 앱에 더하면 `electron.vite.config.ts`의 preload 목록과 renderer 입력 목록 양쪽에 넣는다(한쪽만 넣으면 빈 화면이 뜬다).

- **화면 나누기는 칸이 정확히 둘일 때만이다.** 세 칸 이상을 만드는 길과 떼어 낸 창 안에서 나누는 길을 열지 않는다(결정 0037). 홈·도움말·발표(미리보기) 탭은 칸에 들어가지 못한다.
- **같은 문서가 두 칸에 있을 때 저장은 확인을 받은 뒤에만 쓴다.** 한쪽에서 저장한 뒤 다른 칸에서 또 저장하려 하면 "이 문서가 다른 곳에서 바뀌었습니다"를 먼저 묻고, 사람이 확인한 뒤에만 디스크에 쓴다. 자동 저장은 확인 없이 조용히 미룬다.
- **나눔 기억은 망가진 값을 무시하고, 나눔을 풀면 지운다.** 기억을 읽어 복원할 때 값이 어긋나 있으면 그 값으로 나누지 않는다. 나눔을 풀면 그 기억을 지운다.

- **에이전트 세션은 사람이 시작한 창에만 속한다.** 채널은 그 창의 webContents만 받고, 세션은 그 창이 닫히면 끝난다. 경고 확인과 폴더 검사와 연결 확인은 화면이 아니라 뒷단이 시작할 때마다 다시 한다. 창에는 오류 문장을 보내지 않고 종류만 보낸다(`agentEventView`).
- **세션 MCP 서버의 도구는 `AGENT_MCP_TOOL_NAMES`뿐이다.** 탭 닫기, 자체 편집 세션, 창 없는 파일 만들기를 더하지 않는다. 읽기는 가린 자리를 `{{이름}}`으로 내보내고(`withholdingSlides`, `withholdingOpenDocuments`), 가린 내용이 있는 PPT는 고치지 않는다. 연동의 앱 안 MCP 서버는 출력이 바깥에 약속된 것이라 이 처리를 하지 않는다(결정 0016).

## 이 모듈의 방식

- 에디터의 메인 코드는 패키지가 아니라 상대 경로로 가져온다(`../../../docs/src/main/docs-main`). `electron.vite.config.ts`는 메인에 대해 아무것도 외부화하지 않고 전부 한 번들로 묶는다. 그래서 `apps/*/src/main`을 고친 뒤에는 shell을 다시 빌드해야 한다. 안 하면 변경이 조용히 실행되지 않는다. 렌더러와 preload는 각 에디터의 빌드 결과(`apps/<앱>/out`, 패키징 시 `resources/modules/`)에서 불러오므로 그쪽도 먼저 빌드되어 있어야 한다(`npm run shell`은 `build:all` 뒤에 실행한다).
- 개발 모드에서 preload를 고쳤으면 다시 빌드한다. 낡은 preload는 렌더러를 빈 화면으로 만든다(`npm run dev`의 `predev`가 `tools/build-stale-preloads.mjs`를 돌린다).
- 에디터는 `configure<앱>Runtime({ preloadPath, rendererUrl, rendererFile, … })`으로 자기 빌드 결과의 위치를 주입받는다. 공용 `ai:*` 핸들러는 `registerAiIpc()` 한 번으로 모든 창(문서, 시트, 홈)을 담당한다. 시트 뷰를 `createSheetsView({ includeAiHandlers: false })`로 만드는 이유다.
- 첫 실행 안내의 연결 단계는 `@genoffice/ui`의 연결 도우미(`AiConnectGuide`, 결정 0047)다. 무료 길에는 `FreeAiCards`를 그 자리에 넘기고(`freeContent`), 무료 연결이 이미 있으면 `freeConnected`로 그 길을 펼친다. 띄우지 못한 설치·로그인의 알림(`connection.failed`)은 고른 길의 카드 아래에 `renderAfterCard`로 나온다. 설정 → AI는 도우미 없이 두 카드를 그대로 둔다.
- 무료 연결 카드(`FreeAiCards.tsx`, 규칙은 `free-ai-cards.ts`)는 설정 → AI의 "무료로 쓰기"와 첫 실행 안내의 연결 단계에 같은 부품으로 들어간다. 연결·해제·남은 요청 수는 preload의 `connectFreeAi`·`disconnectFreeAi`·`getFreeAiQuota`가 워드 뒷단의 `ai:free-*` 채널을 부르고, 카드는 설정 파일이 바뀐 알림을 받아 다시 읽는다. OpenRouter 키는 이 화면에 오지 않는다.
- 설정 화면에서 쓰는 AI는 "사용할 AI" 선택 하나로 정해진다. 고급 영역의 제공자 드롭다운은 어느 제공자의 입력란을 보여 줄지만 고른다. 설정은 읽을 때(`readAiSettings`)와 쓸 때(`writeAiSettings`) 모두 `normalizeAiSettings`를 거쳐, 사라진 선택이 다시 저장되지 않는다.
- 홈의 질문 패널은 에디터와 같은 보내기 규칙을 쓴다. `askSendGate`(`src/renderer/src/kb-ask-connection.ts`)는 `packages/ui`의 `aiSendGate`가 내린 판단을 그대로 읽는다. 연결 상태나 설정을 아직 모르면 질문을 붙잡았다가(`askHeldStep`) 실행할 수 있게 되면 시작하고, "연결 필요"로 정해지면 버리고 연결 안내를 보인다. 이 패널만의 차이는 하나다. 첫 연결 안내는 홈 화면이 띄우므로, 안내가 떠 있는 동안에는 패널이 보내지 않고 붙잡아 둔 질문도 시작하지 않는다.
- 첫 연결 안내의 Codex 문장은 `CODEX_MAY_KEEP_HISTORY`로 켜져 있다. 브리지가 대화 이력 파일은 끄지만 Codex가 자체 진단 로그를 남기고, 앱은 그것을 읽을 수도 막을 수도 없기 때문이다.
- 문자열은 세 군데에 있다. 렌더러 사전 `src/renderer/src/strings.ts`(언어 21개가 한 파일에 있고 `zh`가 키 집합을 정한다), 메인 프로세스의 인라인 사전(`src/main/index.ts`의 `tMain`), 도움말 `i18n/help/topics/<id>.<lang>.md`. 도움말 항목은 `help-registry.ts`의 `HELP_TOPICS`에 등록해야 보이고, 모든 언어 파일의 구조는 영어 원본과 같아야 한다(`npm run check:help-langs`).
- **한국어 도움말(`<id>.ko.md`)은 소개 사이트 질문 도우미의 지식베이스다.** 릴리스 태그의 내용이 사이트 저장소 Actions로 들어가고, 도우미는 거기 적힌 것만 답한다. 기능을 바꾸면 도움말도 같이 고쳐야 도우미가 옛 동작을 안내하지 않는다. 제목(`#`·`##`·`###`)이 조각의 이름이 되니 무엇을 다루는 절인지 드러나게 짓는다.
- 새 한글 문서는 홈의 카드, "+" 메뉴, 파일 메뉴에서 만든다(`newHwpTab`, `home:new-hwp`). 다른 새 문서처럼 만든 폴더를 기억해 두고(`rememberPendingDir`), 첫 저장 뒤 한글 저장 훅이 파일을 그 폴더로 옮긴다(`applyPendingDir`). 탭 이름은 저장 전까지 "제목 없는 한글 문서"(`untitledHwp`)다.
- 앱 안 MCP의 `read_deck`은 슬라이드마다 `hidden`(숨김일 때)과 `comments`(메모가 있을 때만, `authorId`·`idx`·`작성자`·`시각`·`본문`)를 낸다. 메모는 가리기 표식 대상이 아니므로 withhold 모드에서도 같은 결과다.
- 한글 문서는 편집기 밖에서 읽기만 한다. 파일 색인·지식 자료는 `parseFileToText`로, 앱 안 MCP의 `read_hwp`(`src/main/mcp/tools/hwp-tools.ts`)는 `hwpToText`로 디스크의 파일을 읽고, 열린 문서 읽기(`open_documents`)는 한글 탭이면 `apps/hwp`의 `hwpReadText`로 저장하지 않은 내용까지 읽는다. 열린 문서를 MCP로 저장하는 길은 한글 탭에 없다. 엔진 WASM은 `electron-builder.cjs`의 `extraResources`가 `Resources/wasm/rhwp_bg.wasm`으로 넣는다.
- 렌더러 CSS의 크롬 색은 토큰만 쓴다(`npm run check:theme-colors`). shell의 강조색(`--accent` 계열)은 `src/renderer/src/home.css`에서 정의한다.
- 구조 작업 프로세스는 메인 번들과 따로 묶인다. `pdf-structure-ipc.ts`가 진입점을 `?modulePath`로 가져오고, 빌드 결과는 `out/main/pdf-structure-process-*.js`다. `electron-builder.cjs`의 `beforePack`이 `assertPdfStructureProcessBuilt`로 이 파일이 있는지 확인하고, 없으면 패키징을 멈춘다. 이 파일이 빠진 설치본은 다른 기능은 되는데 Markdown·EPUB 변환, 그림 꺼내기, 번역 PDF만 실행 중에 실패한다. 번역 PDF에 필요한 `hb-subset.wasm`은 `extraResources`로 `wasm/`에 들어간다(명령줄도 같은 파일을 쓴다).
- 디자인 템플릿 글꼴(`packages/ui/template-fonts`)은 `electron-builder.cjs`의 extraResources 항목 하나로 `resources/template-fonts`에 한 번만 들어간다. 편집기마다 넣지 않고, 편집기는 `templateFontsDir`로 이 폴더를 읽는다. `tests/template-fonts-resource.test.ts`가 항목이 정확히 하나인지, 어느 편집기의 `src`도 그 글꼴 파일을 빌드 자산으로 가져오지 않는지(import, `new URL`, CSS `url()`) 확인한다. 폴더의 `README.md`가 없으면 빌드 설정이 바로 멈춘다(`assertExtraResourceSources`).
- Mac판은 ad hoc 서명만 하고 공증하지 않는다(`electron-builder.cjs` 끝의 `config.mac` 덮어쓰기, 결정 0031). 그래서 `updater.ts`는 Mac에서 업데이트를 내려받지 않고(`SELF_UPDATES`) 업데이트 창을 "다운로드 페이지 열기" 단계로 띄운다. Mac 설치 파일은 `.github/workflows/mac-build.yml`(손으로 실행)이, Linux 패키지(`AppImage`, `deb`, `rpm`)는 `.github/workflows/linux-build.yml`(손으로 실행)이 만든다. Linux에서는 `AppImage`만 스스로 업데이트하고 `deb`·`rpm`은 다운로드 페이지 단계로 띄운다.
- deb의 의존성(`electron-builder.cjs`의 `deb.depends`)은 electron-builder 기본 목록을 그대로 적고, Ubuntu 24.04·Debian 13의 64비트 time_t 전환으로 이름이 바뀐 패키지에는 `libgtk-3-0 | libgtk-3-0t64`처럼 대안을 함께 적는다(설정하면 기본 목록이 통째로 바뀌므로 전체를 적어야 한다). `tests/linux-deb-dependencies.test.ts`가 기본 목록과의 어긋남을 잡고, `linux-build.yml`이 배포 전에 확인한다.
- 패키징은 저장소 루트에서 한다: `npm run dist:win -- -- --publish never`. `--`가 두 번 필요하고, `--publish never`가 없으면 electron-builder가 업로드를 시도한다. xlsx 사이드카는 `target/x86_64-pc-windows-gnu/release/`에 있어야 하므로 Windows에서 MSVC로 빌드했다면 `target/release/xlsx-sidecar.exe`를 그리로 복사한다. OCR 도우미 컴파일에는 Windows SDK가 필요하다.

## 테스트

- 실행: `npm run test -w @genoffice/shell`(또는 이 폴더에서 `npx vitest run`), `npm run typecheck -w @genoffice/shell`. 환경은 `node`다.
- `src/main/index.ts`는 실행 중인 Electron이 있어야 불러올 수 있다. 그래서 배선은 소스 글자를 읽어 고정한다(`tests/subscription-lifetime.test.ts`, `tests/main-locale-tables.test.ts`). 종료 처리나 인라인 사전의 모양을 바꾸면 이 테스트들이 깨진다. 로직은 Electron을 import하지 않는 모듈로 빼서 테스트한다(`settings-ai.ts`, `kb-ask-connection.ts`, `app-routing.ts`).
- 닫은 렌더러 끝내기는 `tests/renderer-disposal.test.ts`, 크래시 기록의 칸과 크기 상한은 `tests/crash-log.test.ts`, 기록·알림·다시 열기는 `tests/crash-watch.test.ts`가 본다.
- PDF 구조 작업(`tests/pdf-structure-*.test.ts`)은 가짜 프로세스로 실행기의 수명(답·취소·탭 닫기 때 끝나는지)과 채널의 경로 검사를 본다. 진입점 배선은 `pdf-structure-wiring.test.ts`, 설정의 보관소 줄은 `settings-result-store.test.ts`·`result-store-ipc.test.ts`가 본다. `beforePack`을 거치는 패키징 테스트(`packaged-cli-version.test.ts`)는 구조 프로세스 파일이 있는 것처럼 가짜 목록을 준다. 확인 조건을 바꾸면 그 가짜도 고친다. 읽기 도우미의 보관소 채널은 `pdf-structure-reading-store.test.ts`, 노트 탭 열기와 글 맡기기는 `pdf-note-tabs.test.ts`가 본다.
- 바꾸면 반드시 테스트하는 것: preload가 내보내는 구독 API(핸들러 없음, 깨진 답), 계정 버튼의 확인 흐름(취소하면 아무것도 실행되지 않는지), 설정 저장 뒤 다시 읽은 값, 제품 정체성(`tests/product-identity.test.ts`: 빌더 설정·`package.json`·HTML 제목·ProgId·저장소 좌표의 일치), 업데이트 피드 설정, 탭 IPC의 인자 검증. 의견 보내기의 세 줄·설문 주소·모든 탭의 도움말 메뉴 배선은 `tests/feedback.test.ts`가 본다.
- 바꾸면 반드시 테스트하는 것(EPUB 탭): 라우팅·메뉴·홈·런타임 배선과 메뉴 문구 21개 언어(`tests/epub-shell-wiring.test.ts`, 소스 글자를 읽어 고정한다), 연결 프로그램 등록(`tests/open-with-icons.test.ts`, `tests/file-associations.test.ts`), 앱 안 MCP 다리(`tests/mcp/open-documents-bridge.test.ts`, `tests/mcp/formats.test.ts`).
- 바꾸면 반드시 테스트하는 것(만들기와 기록): 요청 검사(`tests/generate-request.test.ts`), 저장하지 않은 자료의 차단과 한 번만 맡겨 두기(`tests/generate-session*.test.ts`, `tests/generate-handoff.test.ts`), 자료의 크기·글 길이와 읽을 수 없는 자료의 이유(`tests/generate-materials.test.ts`), 바꾸기와 가린 자리의 이름표(`tests/generate-convert.test.ts`), 시작되지 않은 실행은 기록하지 않는 것·이름 바뀜 따라가기·망가진 파일(`tests/document-links.test.ts`), 다른 파일로 읽기의 가리기와 저장 안 한 파일(`tests/cross-file-redaction.test.ts`), 그룹 밖 파일 읽기의 거절(`tests/kb-ask-scope.test.ts`, `tests/kb-ask-group.test.ts`), `.xmind`가 Windows 기본 연결로 등록되지 않는 것(`tests/file-associations.test.ts`), 한글·마인드맵 "연결 프로그램" ProgId와 아이콘 배선(`tests/open-with-icons.test.ts`), Windows 기본 앱 등록이 확장자별 ProgId로 이어지는 것(`tests/open-with-icons.test.ts`), 앱 안 MCP의 지도(`tests/mcp/open-documents-mindmap.test.ts`).
